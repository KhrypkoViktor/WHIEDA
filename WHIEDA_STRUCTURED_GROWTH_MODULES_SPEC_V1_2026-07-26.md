# WHIEDA: акции, стартовая корзина, ресурсы, мероприятия и рассылки

Версия: 1.0  
Дата: 2026-07-26  
Статус: утвержденное ТЗ следующего этапа после завершения текущего SQL-плана  
Основной контур: текущий prod `n8n + VPS/Postgres + Telegram`  
Редактор данных: существующая Google Sheet `WHIEDA Structured Layer - Products Prices V01`

## 1. Цель релиза

Расширить бесплатный быстрый SQL-советник WHIEDA четырьмя связанными возможностями:

1. Действующие акции.
2. Подбор выгодной первой покупки и стартовой корзины.
3. Каталог полезных групп, каналов и материалов.
4. Мероприятия, напоминания и сегментированные рассылки.

Все пользовательские ответы этого релиза должны формироваться из structured SQL без Dify/RAG и без дополнительного вызова языковой модели.

Главная ценность:

- новичок быстро понимает, что выгодно купить при регистрации;
- партнер видит актуальные акции;
- человек получает нужные группы и материалы своей структуры;
- лидер может сообщить о встрече или новости выбранной аудитории;
- данные редактируются в Google Sheets и появляются в боте максимум через 15 минут.

## 4. Архитектурные правила

### 4.1. Источник правды

- Google Sheets является редактором и master.
- Текущий Postgres является runtime.
- n8n отвечает за синхронизацию, маршрутизацию и отправку.
- Telegram является пользовательским интерфейсом.
- Синхронизация выполняется каждые 15 минут.
- Повторная синхронизация не создает дубли.
- Ошибка одной вкладки не должна удалять последний успешный runtime-срез остальных вкладок.

### 4.2. Скорость

- Ни один запрос этого релиза не отправлять в Dify/RAG.
- Целевой p95 ответа без отправки медиа: не более 3 секунд.
- Данные читать из Postgres одним или минимальным числом запросов.
- Google API не вызывать при пользовательском запросе.

### 4.3. Управление

- Данные меняются через Google Sheets.
- Опасные действия выполняются только после предпросмотра и явного подтверждения.
- Права проверяются по Telegram user id, а не по username.
- Username хранится только как справочная информация.
- Каждый объект принадлежит общему tenant или конкретному tenant/лидеру.

### 4.4. Безопасность изменений

Перед prod-изменениями:

1. Экспортировать live workflow.
2. Сохранить backup затрагиваемых таблиц.
3. Зафиксировать baseline smoke.
4. Подготовить обратимую миграцию.
5. Сначала проверить на тестовом пользователе.
6. Не менять credentials.
7. Не мигрировать базу.

## 7. Модуль подбора первой покупки

### 7.1. Назначение

Собрать человеку понятную стартовую корзину:

- в рамках бюджета;
- под нужный PV;
- с учетом действующих акций;
- с учетом цели покупки;
- с объяснением пользы каждого выбранного товара.

Подбор является коммерческой рекомендацией, а не медицинским назначением.

### 7.2. Термины цены

Зафиксировать алиасы:

- `первичная цена`;
- `первичка`;
- `розничная цена`;
- `цена при регистрации`;

означают один тип цены.

- `партнерская цена`;
- `повторная цена`;
- `повторка`;
- `цена повторной покупки`;

означают второй тип цены.

При расчете использовать реальные поля текущего `Products_Prices`, не создавать копию цен.

### 7.3. Экономическая логика

Для первой покупки товар тем интереснее, чем меньше выгода откладывать его до повторной покупки.

Рассчитать:

```text
price_difference = primary_price - repeat_price
future_discount_ratio = price_difference / primary_price
```

Чем меньше `future_discount_ratio`, тем выше приоритет купить товар при регистрации.

Это только один фактор. Итоговая полезность также зависит от:

- универсальности;
- популярности;
- удобства демонстрации;
- пригодности для подарка;
- удобства первой продажи;
- цели покупателя;
- действующей акции;
- бюджета;
- PV;
- наличия товара;
- ручного бизнес-приоритета.

### 7.4. Правила товаров

Вкладка `Product_Recommendation_Rules`:

- `product_id`;
- `tenant_id`;
- `registration_enabled`;
- `availability_status`;
- `universality_score` — 0-10;
- `popularity_score` — 0-10;
- `demo_score` — 0-10;
- `gift_score` — 0-10;
- `resale_score` — 0-10;
- `personal_use_score` — 0-10;
- `explanation_difficulty` — 0-10;
- `price_sensitivity` — 0-10;
- `business_priority` — 0-10;
- `goal_tags`;
- `audience_tags`;
- `reason_short`;
- `avoid_when`;
- `status`;
- `owner`;
- `updated_at`.

Стартовые бизнес-гипотезы занести как `draft`, затем Виктор утверждает строки:

- очки: высокий `universality/demo/gift`;
- стельки: высокий `universality/demo/gift`;
- активатор: высокий `universality/demo/business_priority`;
- специализированные товары: предлагать только при совпадении цели;
- дорогие и громоздкие товары: не ставить в базовую корзину без достаточного бюджета или явного запроса;
- массажные товары: повышать приоритет для массажистов и людей с соответствующим интересом.

Не зашивать эти оценки навечно в n8n. Они редактируются в Sheet.

### 7.5. Шаблоны корзин

Вкладка `Starter_Basket_Templates`:

- `template_id`;
- `tenant_id`;
- `title`;
- `goal`;
- `budget_min`;
- `budget_max`;
- `target_pv_min`;
- `target_pv_max`;
- `required_product_ids`;
- `preferred_product_ids`;
- `excluded_product_ids`;
- `description`;
- `priority`;
- `status`;
- `owner`;
- `updated_at`.

Начальные цели:

- `balanced` — сбалансированный старт;
- `personal` — для личного использования;
- `demo` — для демонстраций;
- `gift` — для подарков;
- `resale` — для первых продаж;
- `pv` — достижение нужного PV;

### 7.6. Входные данные подбора

Минимально нужен бюджет или целевой PV.

Дополнительные параметры:

- цель;
- обязательный товар;
- исключенный товар;
- страна;
- tenant;
- допустимое отклонение бюджета;
- допустимое превышение PV.

Примеры:

- «Что выгодно взять при регистрации на 300 BYN?»
- «Собери корзину на 500 рублей для демонстраций».
- «Мне нужно 100 PV».
- «Подбери старт, но без активатора».
- «Хочу очки и что-нибудь универсальное».

### 7.7. Уточнения

Если нет бюджета и PV:

```text
Соберу. На какой бюджет или PV ориентируемся?
```

После ответа спросить цель, если она не была указана:

```text
Что важнее: личное использование, демонстрации, подарки, первые продажи или просто сбалансированный старт?
```

Не задавать больше двух обязательных уточнений. Если цель не указана, использовать `balanced`.

### 7.8. Алгоритм

1. Получить активные товары и цены из текущего runtime.
2. Исключить отсутствующие и запрещенные для регистрации товары.
3. Применить tenant и страну.
4. Применить обязательные и исключенные товары.
5. Подтянуть активные акции.
6. Рассчитать `future_discount_ratio`.
7. Рассчитать полезность товара по выбранной цели.
8. Собрать допустимые корзины в пределах бюджета/PV.
9. Не добавлять один SKU несколько раз, если правило явно не разрешает количество больше 1.
10. Выдать до трех вариантов:
    - `Сбалансированный`;
    - `Максимум пользы для выбранной цели`;
    - `Максимум PV`, только если PV важен.
11. Не показывать почти одинаковые варианты.
12. Для каждого товара дать одно короткое объяснение.

Начальная формула оценки:

```text
score =
  goal_score * 0.35 +
  universality_score * 0.15 +
  business_priority * 0.15 +
  demo_score * 0.10 +
  gift_score * 0.05 +
  resale_score * 0.05 +
  registration_price_score * 0.10 +
  promotion_score * 0.05
```

Где:

- `goal_score` выбирается из соответствующего поля цели;
- `registration_price_score` выше при меньшем `future_discount_ratio`;
- `promotion_score` равен 10 при применимой активной акции, иначе 0.

Веса хранить в конфигурации, а не размазывать по нескольким Code nodes.

Если каталог небольшой, использовать детерминированный перебор или bounded knapsack. Не использовать LLM.

### 7.9. Формат ответа

```text
🛒 Сбалансированный старт на <сумма>

1. <Товар> — <цена>, <PV>
   <Почему вошел в корзину>

2. <Товар> — <цена>, <PV>
   <Почему вошел в корзину>

Итого: <сумма>, <PV>.
Экономия/выгода по акции: <если применимо>.

Могу пересобрать корзину под другой бюджет или сделать вариант для демонстраций.
```

Не обещать доход, продажу товара или медицинский результат.

### 7.10. Контекст

Сохранять:

- бюджет;
- цель;
- target PV;
- выбранный вариант;
- товары;
- примененную акцию.

Follow-up должны работать:

- «А на 500?»
- «Без очков».
- «Добавь активатор».
- «Сделай для подарков».
- «Сколько будет PV?»
- «Покажи второй вариант».

## 9. Мероприятия

### 9.1. Принцип

Не создавать новую систему. Расширить существующие встречи и текущий broadcast/delivery worker.

Google Sheet дает удобный редактор событий. Команда `/meeting` остается быстрым способом создать одно событие из Telegram.

Оба пути должны приводить к одной runtime-сущности и одному механизму напоминаний.

### 9.2. Поля

Вкладка `Events`:

- `event_id`;
- `tenant_id`;

- `event_type`;
- `description`;
- `starts_at`;
- `ends_at`;
- `timezone`;
- `country`;

- `online_url`;
- `contact`;
- `audience_segment`;
- `leader_id`;
- `image_url`;
- `source_url`;
- `reminder_offsets` — например `24h,1h`;
- `status` — `draft/confirmed/cancelled/completed`;
- `owner`;
- `updated_at`.

Типы:

- `office_meeting`;
- `training`;
- `leader_visit`;
- `presentation`;
- `online`;
- `informal`;
- `company`;
- `other`.

### 9.3. Пользовательские запросы

- «Какие ближайшие мероприятия?»
- «Что будет в Минске?»
- «Когда следующая встреча?»
- «Есть обучение онлайн?»
- «Куда приехать на встречу?»

Выдавать только будущие `confirmed` события, доступные пользователю.

### 9.4. Напоминания

- использовать существующий dispatcher;
- стандартно за 24 часа и 1 час;
- дополнительные offsets брать из события;
- уникальность доставки: `event_id + reminder_offset + telegram_user_id`;
- изменение времени отменяет старые неотправленные задания и создает новые;
- отмена события отменяет все pending reminders;
- повторный sync не создает задания повторно;
- после отмены отправлять уведомление только тем, кому уже пришло хотя бы одно приглашение или напоминание.

- защита от дублей.

### 10.2. Роли

На первом этапе:

- Виктор: super admin, все tenant;
- лидер: только собственный tenant и разрешенные сегменты;
- администратор: только явно выданные права;
- обычный пользователь: не может создавать рассылки.

Авторизация только по Telegram user id и существующему реестру ролей.

### 10.3. Сегменты

- `all_active`;

### 10.4. Предпросмотр

До подтверждения показать:

- тип сообщения;
- текст;
- фото, если есть;
- выбранный tenant;
- выбранный сегмент;
- примененные фильтры;
- точное число получателей;
- число исключенных;
- время отправки;
- одноразовый id подтверждения.

Без подтверждения ничего не отправлять.

### 10.5. Тематические подписки

- `system`;
- `promotions`;
- `events`;
- `training`;
- `business`;
- `leader_news`.

Системные критичные сообщения можно отправлять всем активным пользователям tenant только по решению super admin.

Остальные категории учитывать по подписке пользователя.

## 11. Синхронизация

Расширить текущий Sheet -> Postgres sync.

Для каждой новой вкладки журналировать:

- `run_id`;
- `sheet_name`;
- `started_at`;
- `finished_at`;
- `rows_read`;
- `rows_inserted`;
- `rows_updated`;
- `rows_disabled`;
- `rows_rejected`;
- `status`;
- `error_text`;
- `source_revision`.

Правила:

- cron каждые 15 минут;
- ручной безопасный запуск для теста;
- upsert;
- валидация обязательных полей;
- ошибочная строка не блокирует корректные строки;
- ошибочная строка попадает в sync report;
- удаление строки из Sheet не должно молча физически удалять runtime-запись;
- использовать status/soft disable;
- last successful snapshot сохраняется.

## 13. Неопределенность и fallback

Не отвечать «не знаю» на распознаваемые темы.

Если пользователь пишет «акция»:

```text
Показать все действующие акции или проверить акцию на конкретный товар?
```

Если пишет «что взять»:

```text
Помогу собрать стартовую корзину. На какой бюджет или PV ориентируемся?
```

Если пишет «группа»:

```text
Какая нужна: отзывы, обучение, продукты, бизнес или мероприятия?
```

Если пишет «встреча»:

```text
Показать ближайшие мероприятия или найти событие в вашем городе?
```

Уточнение должно направлять к известному structured intent.

## 14. Тесты

### 14.1. Sync

Проверить:

- новая акция появляется максимум за 15 минут;
- изменение даты сразу меняет активность;
- завершенная акция исчезает из выдачи;
- повторный sync не создает дубль;
- битая строка видна в sync report;
- предыдущий успешный срез сохраняется при ошибке Google API.

### 14.2. Подбор корзины

Минимум 30 кейсов:

- бюджет ниже минимального товара;
- точный бюджет;
- большой бюджет;
- только target PV;
- бюджет и PV вместе;
- обязательный товар;
- исключенный товар;
- товар отсутствует;
- активная акция;
- акция завершена;
- personal/demo/gift/resale/balanced;
- follow-up с изменением бюджета;
- follow-up с исключением товара;
- одинаковый запрос дает одинаковый результат;
- сумма и PV пересчитаны точно;
- нет обращения в Dify.

### 14.3. Ресурсы

Минимум 15 кейсов:

- общая группа отзывов;
- tenant-группа;
- лидерская группа;
- закрытый ресурс;
- битая ссылка;
- категория без результатов;
- опечатка;
- follow-up «а по бизнесу?»;
- пользователь другого tenant не видит чужие приватные ссылки.

### 14.4. Мероприятия

Минимум 15 кейсов:

- ближайшие события;
- фильтр по городу;
- online;
- отмененное событие;
- перенос времени;
- два напоминания;
- отсутствие дублей;
- смена времени отменяет старые pending;
- событие другого tenant не показывается.

### 14.5. Рассылки

Проверить:

- обычный пользователь не создает рассылку;
- лидер не отправляет в чужой tenant;
- preview показывает точное число;
- без confirm отправки нет;
- повторный confirm не дублирует;
- blocked user становится inactive;
- тематическая отписка учитывается;
- итоговый отчет сходится с delivery log.

### 14.6. Общая регрессия

После каждого блока запускать:

- P0;
- product regression;
- functional smoke;
- новый growth smoke;
- health check.

Ни одна новая функция не должна ухудшить:

- карточки товаров;
- цены и PV;
- фото и видео;
- follow-up контекст;
- текущие встречи;
- текущую рассылку;
- gap/review;
- latency SQL fast path.

- общий P0 и product regression остаются зелеными;
- автоматические тесты новых модулей зелены;
