# Шаблон задачи исполнителю

Копировать в `PROCESS/<task-id>/TASK.md`. Один пакет — одна задача. Если
исполнителю приходится дочитывать канон целиком, чтобы понять, что делать,
пакет собран плохо.

---

## Задача

Один результат одной фразой. Не список пожеланий.

## Тип изменения

Отметить один: `partner` / `article` / `prices` / `shared-code` /
`infrastructure`. От типа зависит, какие файлы разрешены и какие проверки
обязательны. Смешивать типы в одном пакете нельзя — именно так цена меняется
«заодно» с версткой.

## База

- repo:
- branch:
- base SHA:
- worktree:

База называется явно. Текущий checkout не считается production-базой по
умолчанию.

## Разрешённые файлы

Явный список путей или каталогов. Всё остальное — вне пакета, включая общие
шаблоны, CSS, калькулятор и nginx.

## Источники

Откуда брать данные и что считать master. Ссылки на конкретные файлы, а не на
«канон». См. `PROCESS/engineering-order-20260905/SOURCE_MAP.md`.

## Что запрещено

Минимум: production, чужие worktree и ветки, цены вне ценовой задачи, массовая
архивация, рефакторинг вне задачи. Дополнить под конкретную задачу.

## Команды проверки

Точные команды с ожидаемым результатом. Например:

```bash
node --test tools/doc-check/test-doc-check.mjs
npm run test:unit
npm run build
```

## Критерий готовности

Измеримый. «Работает» — не критерий. «`npm run test:unit` зелёный, две
негативные фикстуры дают nonzero» — критерий.

## Отчёт

Что изменено; repo/branch/SHA или незакоммиченный diff; что фактически
проверено; что не проверено; следующий шаг. «Готово локально», «принято на
staging» и «опубликовано» не взаимозаменяемы.
