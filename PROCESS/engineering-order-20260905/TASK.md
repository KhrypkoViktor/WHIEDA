# WWC: порядок разработки и автоматические защиты

Дата: 2026-09-05. Владелец: Виктор. Исполнитель: обычный разработчик; лид принимает
каждый блок отдельно. Статус: ready for local implementation, не разрешение на deploy.

## Цель и границы

Добавление партнёра/статьи должно менять только его данные и разрешённые индексы.
Цена, фото другого партнёра, калькулятор, общий дизайн и production не должны
меняться попутно. Одних инструкций мало: нужны проверки, которые останавливают ошибку.

Не переписывать сайт, не переносить framework/БД, не строить новый CI-сервис,
не менять Core/n8n/Sheets, цены/публичные тексты/действующие профили, не делать deploy.
Не чистить существующие worktree и не сливать весь исторический snapshot.
Активное ТЗ по скорости `WWC_SENIOR_REVIEW_TZ_V1_2026-09-05.md` не включать в этот пакет.

Старт: корневой AGENTS, STATE рядом, AGENTS выбранного website-worktree. Проверить
Git. Если общие scripts/package.json уже заняты performance-исполнителем, делать
свои инструменты/fixtures отдельно; подключение к release:verify оставляет интегратор.
Сначала блок A. Не менять общий рендер, пока лид не принял его результат.

## A. Карта состояния и проверяемый процесс

1. Создать отдельный task-worktree сайта от явно выбранного принятого commit.
   Не считать текущий checkout автоматически production-базой. Без подтверждённой
   базы допускается read-only карта и инструменты, но не релизная интеграция.
2. Сделать `PROCESS/<task-id>/STATE.md`: задача/владелец, repo, worktree, branch,
   base SHA, allowed paths, исходный diff, свои изменения, проверки, следующий шаг.
   Это контекст, не альтернативный Git. Сгенерировать Git-снимок автоматически.
3. Подготовить компактный реестр worktree: путь, branch/HEAD, dirty, уникальные
   commits относительно указанной базы, статус задачи (unknown допустим).
   Владелец не определяется только по имени ветки/автору. Ничего не удалять.
4. Подготовить `ENVIRONMENTS.md` в пакете: домен -> host -> listener -> docroot ->
   code artifact -> runtime config -> API/БД. Каждое значение имеет evidence/date
   или `unverified`. Production SHA из переписки — reported, не verified.
   Онлайн `nginx -T`/SSH в этом блоке не выполнять: список нужных проверок передать лиду.
5. Проверить активные входные ссылки. Исторические missing хранить отдельно;
   нельзя возвращать старое ТЗ из архива в действующие только ради зелёной проверки.
   Исправить реальный относительный путь сайта в индексе внешнего pipeline отдельным
   согласованным doc-патчем; внешние инструкции не копировать в сайт целиком.
6. Реализовать локальный doc-check с явным manifest активных обязательных документов
   и связей. Он не сканирует миллионы токенов архива, не требует доступов/секретов.
   Negative fixture: отсутствующая активная ссылка -> nonzero; historical -> warning.

Выход A: карта источников (см. ниже), ENVIRONMENTS, task template, doc-check + тесты,
точные команды запуска из package scripts/README. Факты не подменены догадками.

лиду; не объединять всё самостоятельно. Не считать схожие таблицы дубликатами.

## B. Три простых конвейера и UI-границы

Сначала оформить короткие runbooks в существующих website `docs/`, расширяя
найденные документы. Полноценный бот/админку для onboarding сейчас не строить.

### Партнёр

1. Переиспользовать PARTNER_ONBOARDING_STANDARD и INFORMATION_REQUEST_TEMPLATE.
   Проверять имя, стабильный ID/ref, свободный/разрешённый subdomain, контакт,
   разрешение на фото, статус публикации. Бизнес-поля и tenant/owner нельзя смешивать.
2. Сделать локальный валидатор кандидата и diff-plan: повторный ввод не создаёт
   дубль; занятое имя/невалидный контакт/чужой owner -> ошибка; нет фото -> только
   явный no_photo. Не подключать Sheets запись в локальном validator.
3. Фото: хранить исходник отдельно от производных, уникальный путь партнёра,
   размеры/ratio взять из фактического компонента. Focal point параметром данных;
   не писать CSS под фамилию. Попросить исходное фото без ручной обрезки.
4. Выход: профиль-кандидат, медиа manifest, diff, порядок штатной синхронизации,
   preview и smoke. Если общий шаблон ещё требует индивидуального .astro-кода,
   зафиксировать это ограничение и отдельный минимальный кодовый срез для лида.
   Не объявлять data-only процесс реализованным до проверки двух разных профилей.
5. Smoke локально: два разных партнёра, корень, unknown/disabled ref; переходы
   между ними не оставляют чужую фотографию/CTA/владельца заявки. Заявки mock/capture.

### Статья

1. Вход: утверждённый текст, slug/title, источники, категория, её медиа и dates.
   Путь pipeline подтверждается владельцем; NotebookLM не обязательная зависимость.
2. Существующие ArticleHero/ArticleNext/индекс. Никаких локальных кнопок/шрифтов,
   отдельных массивов рекомендаций/дат. Разрешены только статья, её медиа и
   перечисленные индексы; shared code отдельно согласуется.
3. Проверки: уникальный slug, даты, H1/структура, ссылки/изображения, соответствие
   согласованному тексту, локальный HTML без JS, mobile/desktop. Без массовой
   правки языка и SEO-настроек остальных страниц.

### Каталог и цены

1. Существующий master — Products_Prices, manifest в WORK. URL официальных RU/BY/EU
   установить по принятым материалам, не по поисковой выдаче/догадке. EU-кандидат
   уже описан в `PROCESS/GLM_EU_PRICES_READ_ONLY_TZ_2026-09-04.md` корневого repo.
2. Сбор read-only в пакет кандидата. Каждая строка: SKU, официальный title,
   market, currency, price_type, amount, PV (или null), URL/file, дата и evidence.
   Не переводить W$ в RUB/BYN без утверждённого правила. Не менять первичную
   цену повторной; неизвестное/отсутствующее не равно нулю/удалённому товару.
3. При login/CAPTCHA/access-denied не обходить авторизацию и не ретраить часами.
   Записать недоступный источник и запросить выгрузку/скрин у владельца.
   Ручная строка также сохраняет provenance; распознанные суммы проверяются.
4. Сравнить candidate/master: новые/изменённые/отсутствующие/неоднозначные.
   Сопоставлять по SKU; предложенный alias требует решения. Отдельно фото,
   название и цена, чтобы price-import не затирал контент/медиа.
5. Применение только после утверждения конкретного diff/hash владельцем через
   существующий импорт. В этом ТЗ реализовать validator/fixtures, не реальный import.

### UI

Создать небольшой локальный эталон компонентов: кнопки/ссылки, поля/select,
модалка, карточка, currency/language control. Использовать существующие компоненты.
У золотой primary CTA проверить normal/hover/focus/disabled; статусные цвета
не запрещать. Линтер отслеживает НОВЫЕ page-local цвета/шрифты, а не требует
одним коммитом исправить весь старый CSS. Исключения только явным списком с причиной.
Скриншоты 390x844 и 1440x900, клавиатура, открытие/закрытие, длинные имена/тексты.

## C. Запрет ошибочного пакета и релизная приёмка

1. Сделать `change-scope` validator по base/head И локальному diff; untracked
   файлы тоже учитываются. Тип задачи partner/article/prices/shared-code.
   Partner/article allowlist не допускает общие шаблоны, CSS, calculator, nginx.
   Файл общего реестра проверяется по изменённым записям, а не разрешается целиком.
   Не запускать тяжёлый build на каждый текстовый символ; gates зависят от типа.
2. Негативные fixtures: partner меняет чужой контакт/цену; article меняет CSS;
   цена смешивает currency/price_type; generated twin не соответствует источнику;
   broken photo; новая зелёная primary CTA; неверный ref в mock lead.
   Каждый намеренный дефект должен давать nonzero, без обращения к production.
3. Расширить существующие тесты, не дублировать их новым фреймворком. Команды на
   текущем checkout: `npm run check`, `npm run test:unit`, `npm run test:smoke`,
   `npm run test:e2e`, `npm run test:visual`, `npm run release:verify`.
   Проверить package.json выбранной ветки: check:seo сейчас отсутствует в основном
   checkout, но упомянут в каноне/другой ветке. Не объявлять его выполненным.
4. Перед локальными build/test проверить, не делают ли скрипты сетевые записи,
   не перезаписывают ли принятые данные. Runtime mocks и явный base URL; для
   partner A/B, каталога, корзины, формы и SEO должны быть локальные сценарии.
5. Предложить лидy один проверенный release-gate и manifest-контракт:
   commit + artifact SHA256 + config/data versions + результаты тестов + среда.
   Postbuild timestamp может менять байты: хешировать окончательный артефакт,
   не «вчерашний dist». Метаданные не править вручную после установки.
6. Реальные deploy-скрипты/CI hooks подключает интегратор отдельным reviewed
   патчем. До подключения gate честно называется локальным, не защитой production.
   Ограничение prod/dev/staging задаётся явной целью, без production default.

## Приёмка и передача

Пакет A -> review -> B -> review -> C. Не ждать лида после каждого файла внутри
одного блока. Не добавлять массовую архивацию или переделку дизайна «заодно».
Коммиты по блокам в task-ветке; push/merge/deploy отдельно разрешаются.

Один REPORT на блок: repo/base/head, список diff, команды/exit codes,
положительные/отрицательные тесты, ссылки на скриншоты, ограничения.
STATE обновить. Для полностью data-only onboarding доказать, что у двух тестовых
партнёров shared code и цены имеют прежние хеши, данные/фото/CTA различаются
правильно, а калькулятор и mock-заявки проходят. Это критерий, не обещание.

Отдельный следующий контентный срез: улучшить язык pipeline по 2-3 неудачным
результатам и принятому эталону. Не подмешивать это к инженерному блоку.
