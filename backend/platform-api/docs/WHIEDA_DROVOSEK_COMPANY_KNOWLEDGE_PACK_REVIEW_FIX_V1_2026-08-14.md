# WHIEDA: Company Knowledge Pack V1.1 Review Fix

## Цель

Доработать уже собранный `qa/company_knowledge/` так, чтобы он стал чистым
кандидатом для будущего публичного слоя советника. Это работа с данными и QA.
`app/**`, Telegram, n8n, Postgres, Google Sheets и production не менять.

## Почему нужен review-fix

В V1 в одном наборе лежат три разных типа информации:

1. Факты о WHIEDA / FOHERB, которые может спросить обычный человек.
2. Внутренняя архитектура нашей платформы: Core, tenant, SQL, конвейер контента.
3. Контакты и роли конкретных партнёров.

Их нельзя смешивать в одном публичном ответе. Вопрос «расскажи о WHIEDA» не
должен отвечаться внутренней схемой платформы или данными о владельце сервиса.

## Block A. Развести три слоя

В каждом `fact` и `question` добавить поле `audience_layer`:

- `company_public` — компания, бренд, производство, история, технологии,
  официальные события и публичные представители;
- `partner_network` — наставник, конкретная структура, персональный контакт,
  ref, локальное мероприятие;
- `platform_internal` — Core, SQL, tenant, архитектура, внутренний контентный
  конвейер, владелец платформы.

Правила:

- `company_public` — единственный слой для будущего общего вопроса
  «о компании»;
- `partner_network` не выдаётся в общий ответ без текущего ref/структуры или
  прямого вопроса о конкретном человеке;
- `platform_internal` остаётся внутренней документацией и в Telegram-ответы
  не попадает;
- не удалять строки и не терять provenance: переклассифицировать их.

## Block B. Публичный минимальный набор

Собрать `COMPANY_PUBLIC_REPLY_CANDIDATES_V1.tsv` только из
`company_public` фактов со статусом `accepted`.

Для каждого ответа обязательны:

- `reply_id`;
- `question_examples`;
- `answer_text`;
- `fact_ids`;
- `source_ref`;
- `owner_status`;
- `answer_length` (`short` / `full`).

Сделать минимум шесть намерений, даже если часть из них пока `pending_owner`:

1. Что такое WHIEDA.
2. Чем занимается компания.
3. История и год основания.
4. Где производят товары.
5. Кто публичные представители.
6. Где смотреть официальные новости и мероприятия.

Нельзя использовать как публичный ответ:

- «WHIEDA строит систему контент → сайт → Core...»;
- описание Core, SQL, tenant, RAG;
- «Владелец платформы и продающего языка...»;
- личные ref-ссылки или телефоны партнёров;
- пустые данные как будто это факт.

## Block C. Контакты и люди

Создать отдельный `PARTNER_NETWORK_CONTACTS_CANDIDATES_V1.tsv`.

- Оставить только уже существующие данные из snapshot.
- Не добавлять номера телефонов в общий public слой.
- Для каждого контакта явно указать `requires_ref_context=yes|no`.
- Для локальных встреч отделить `event_public` от персонального наставника.
- `prepared_not_routed` не считать автоматически доступным пользователю
  контактом.

## Block D. Owner request, который реально удобно заполнить

Переписать `COMPANY_INFORMATION_REQUEST_FOR_OWNER.md`:

- вначале один короткий блок «вставьте ответ прямо после двоеточия»;
- максимум 12 строк, без терминов `provenance`, `layer`, `runtime`;
- отдельно отметить необязательные пункты;
- не требовать сразу номера сертификатов, если можно дать ссылку на официальный
  PDF/страницу;
- добавить готовый шаблон публичного описания компании на 5–7 предложений,
  который владелец может поправить, а не писать с нуля.

## Block E. QA и отчёт

Добавить проверки:

1. Каждый accepted `company_public` факт имеет непустой `fact_text`, источник
   и `owner_status=accepted`.
2. `platform_internal` не попадает в `COMPANY_PUBLIC_REPLY_CANDIDATES_V1.tsv`.
3. `partner_network` не попадает туда без явного `requires_ref_context`.
4. Pending-owner вопросы не получают выдуманный `answer_text`.
5. Все строки старого V1 сохранены: `fact_id` встречается ровно в одном из
   слоёв или в явном архивном registry.
6. Ответ «что такое WHIEDA» содержит только company-public факты.

Команды должны проходить:

```bash
python qa/company_knowledge/build_company_knowledge_pack.py
python qa/company_knowledge/run_company_knowledge_pack.py --offline
python -m pytest backend/platform-api/tests/test_company_knowledge_pack.py -q
```

Создать `COMPANY_KNOWLEDGE_PACK_REVIEW_FIX_LOCAL_REPORT.md` с таблицей:
`company_public / partner_network / platform_internal / pending_owner`.

## Границы

- Не подключать данные к Core и не менять его ответы.
- Не менять существующий master snapshot.
- Не публиковать в Sheets.
- Не делать допущений о годе основания, заводе, сертификатах, географии или
  публичных лицах: такие сведения остаются `pending_owner`, пока нет
  подтверждённого источника.
- В конце: один focused commit только для `qa/company_knowledge/`, теста и
  отчёта.
