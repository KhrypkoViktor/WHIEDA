# WHIEDA: идеальный слой быстрых SQL-ответов

Дата: 2026-07-25  
Горизонт: ближайшие 10-14 рабочих дней  
Статус: главное исполняемое ТЗ текущего цикла  
Продукт: `WHIEDA Structure Basic`

### Уточнение владельца от 2026-07-26

- `batch_*.jsonl`, подготовленные Claude, считаются кандидатным источником для алиасов, FAQ, возражений и regression.
- Медицинские утверждения из таких пакетов не публикуются автоматически: только в отдельный medical review.
- Цель hot path SQL: p95 ответа пользователю 1-3 секунды; измеряется по live execution, а не по задержке polling-теста.
- Только этот агент меняет n8n, Postgres и prod.

## 1. Решение

WHIEDA разделяется на два продукта, даже если они работают в одном Telegram-боте.

### Structure Basic

Быстрый справочник для сайта, общей структуры и бесплатного доступа:

- отвечает за 1-2 секунды;
- закрывает типовые вопросы без LLM;
- использует Google Sheets как редактор и Postgres как runtime;
- отвечает по товарам, ценам, PV/W$, применению, ограничениям, материалам, сравнению, бизнес-FAQ и возражениям;
- понимает алиасы, опечатки и короткие продолжения;
- при неоднозначности задает один конкретный уточняющий вопрос;
- не уходит в Dify/RAG для приветствий и структурированных запросов.

### Partner PRO

Будущий платный нейрокоуч:

- глубокий разбор нескольких вопросов;
- RAG по внутренней библиотеке;
- обучение, домашние задания и проверка;
- мотивация и сопровождение;
- создание материалов;
- живая модель и интернет;
- персональные лимиты и подписка.

Partner PRO не входит в текущий двухнедельный цикл. Текущий цикл должен сделать Structure Basic самостоятельным продаваемым продуктом и надежным фундаментом для PRO.

## 2. Цель цикла

Пользователь задает обычный вопрос своими словами и получает:

1. точный ответ из структурированной базы;
2. подходящее фото или ссылку на материал, если они нужны;
3. один разумный следующий шаг;
4. конкретное уточнение, только если без него невозможно ответить.

Система не должна:

- отвечать общим «я не понял» там, где можно распознать товар или намерение;
- обещать передачу человеку, если реальной передачи нет;
- шутить вместо помощи;
- отправлять приветствия и «что ты умеешь» в RAG;
- повторять один и тот же ответ;
- путать базовый товар и PRO;
- терять контекст после фото, цены, сравнения или уточнения;
- отправлять structured-запрос в Dify;
- менять утвержденные продающие тексты без прямого решения владельца.

## 3. Исходное состояние

Уже работает и не переделывается без найденной ошибки:

- live workflow `advisor-whieda-phase1`;
- Google Sheets -> Postgres каждые 15 минут;
- карточки, цены, PV, фото, видео, сравнение, алиасы и follow-up;
- фото первым без caption, текст вторым;
- товарный smoke `27/27`;
- feature smoke `9/9`;
- SQL-слои `Business_FAQ` и `Business_Objections`;
- русский fallback;
- review queue и runtime gap-механика;
- отдельный глубокий маршрут Dify.

Перед началом первого цикла нужно повторно подтвердить baseline и сохранить свежий export workflow.

## 4. Целевые показатели

К концу цикла:

- не менее 95% вопросов из поддерживаемых тем закрываются SQL;
- 100% приветствий, smalltalk и capability-запросов отвечают без Dify;
- 100% цен, SKU, PV, фото, видео и сравнений отвечают без Dify;
- доля общего fallback в тестовом корпусе не выше 2%;
- не менее 90% неоднозначных вопросов разрешаются за одно уточнение;
- не более двух уточнений подряд;
- P0 smoke: 100%;
- полный regression smoke: не ниже 98%;
- structured-запросов, ошибочно ушедших в Dify: 0;
- дублей текста, двойных фото и caption: 0;
- p95 времени SQL-ответа: не более 2 секунд;
- каждая ошибка имеет `case_id`, маршрут, execution id и классифицированную причину;
- повторный запуск цикла не создает дубли данных и одинаковые gaps.

## 6. Архитектура одного запроса

Каждый запрос проходит одинаковый конвейер.

### Шаг 1. Нормализация

- привести регистр;
- убрать лишнюю пунктуацию и повторные пробелы;
- сохранить исходный текст отдельно;
- распознать упоминание бота;
- нормализовать `ё/е`;
- подготовить варианты транслитерации;
- не удалять значимые числа, `PV`, `W$`, `PRO`.

### Шаг 2. Мгновенные системные намерения

До любого товарного поиска проверить:

- greeting;
- smalltalk;
- capabilities;
- help;
- menu.

Ответы хранятся в SQL и отдаются немедленно.

### Шаг 3. Определение намерения

Определить, что хочет пользователь:

- карточку;
- цену;
- PV/W$;
- применение;
- ограничения;
- фото;
- видео;
- документ;
- сравнение;
- подробности;
- бизнес-FAQ;
- возражение;
- другое поддерживаемое действие.

Одно сообщение может содержать несколько структурированных намерений.

### Шаг 4. Поиск сущности

Искать:

1. точное название;
2. утвержденный алиас;
3. контекст последнего товара;
4. нормализованный алиас;
5. fuzzy-match с безопасным порогом;
6. несколько кандидатов для уточнения.

Нельзя молча выбирать товар при близких кандидатах. Если найдены базовый Активатор и PRO, бот предлагает оба варианта.

### Шаг 5. Проверка обязательных данных

Для каждого намерения определить обязательные слоты:

- `product_id`;
- тип цены;
- второй товар для сравнения;
- вид материала;
- направление подробного ответа.

Если не хватает ровно одного слота, задать один конкретный вопрос.

### Шаг 6. Получение ответа

Ответ берется из соответствующей structured-таблицы. Dify не вызывается.

### Шаг 7. Сборка сообщения

- не повторять заголовок внутри первого предложения;
- не дублировать блоки;
- не выводить внутренние инструкции;
- не показывать пустые секции;
- прикладывать только релевантный материал;
- давать один короткий CTA;
- соблюдать правило `фото -> текст`.

### Шаг 8. Контекст

Сохранить:

- последний подтвержденный товар;
- последнее намерение;
- последнюю выданную карточку;
- незакрытое уточнение;
- список кандидатов;
- время жизни контекста.

Новый явно названный товар всегда сильнее старого контекста.

### Шаг 9. Телеметрия

Записать:

- нормализованный вопрос;
- распознанные намерения;
- найденные сущности;
- route;
- источник;
- потребовалось ли уточнение;
- latency;
- был ли fallback;
- execution id.

## 8. Система уточняющих вопросов

Создать `Clarification_Prompts`.

Минимальные поля:

- `clarification_key`;
- `reason`;
- `prompt_text`;
- `button_options`;
- `max_attempts`;
- `fallback_menu`;
- `enabled`;
- `owner_state`.

Уточнение должно быть связано с конкретной причиной.

### Неясен товар

> Вы про Активатор клеток или Активатор клеток PRO?

### Назван товар, но нет задачи

> Активатор клеток знаю. Что показать: кратко о приборе, применение, цену, отличия PRO, фото или видео?

### Цена без товара

> Цену какого товара посмотреть?

### Сравнение без второго товара

> С чем сравнить Активатор клеток?

### Неясное «подробнее»

> Что раскрыть подробнее: применение, ситуации, опыт людей, механизм, исследования или материалы?

### После двух неудачных уточнений

> Пока не смог точно определить запрос. Выберите: товар, цена/PV, применение, сравнение, фото/видео или бизнес-вопрос.

Запрещенные формулировки:

- «я ничего не понял»;
- «задайте вопрос по-другому» без вариантов;
- «передам специалисту» без реального действия;
- случайная шутка;
- выдуманный ответ.

## 9. Последняя честная ступень fallback

Полностью исключить неизвестность невозможно. Нужно исключить тупой ответ.

Лестница fallback:

1. повторная нормализация;
2. алиасы и опечатки;
3. контекст;
4. fuzzy-кандидаты;
5. конкретное уточнение;
6. меню поддерживаемых направлений;
7. честное сообщение и deduplicated gap.

Финальный текст:

> В базе пока нет готового ответа именно на этот вопрос. Я записал пробел. Сейчас могу помочь с товарами, ценами/PV, применением, сравнением, фото/видео или бизнес-вопросами.

Фраза «записал пробел» допустима только после успешной записи gap.

## 10. Вопросы из нескольких частей

Structure Basic должен разбирать простые составные сообщения без LLM:

- нумерованные списки;
- вопросы, разделенные переносами;
- конструкции «цена и PV»;
- «покажи фото и расскажи отличие PRO»;
- «сколько стоит, как использовать и есть ли видео».

Правила:

- максимум три structured-намерения в одном ответе;
- каждое намерение получает короткий отдельный блок;
- известные части отвечаются сразу;
- уточняется только неизвестная часть;
- нельзя повторять полную карточку для каждого подпункта;
- при сложном свободном сообщении предложить выбрать главный вопрос, не вызывать RAG в бесплатном режиме.

## 12. Работа с 900 источниками

Сырые материалы не публикуются напрямую и не загружаются всей массой в RAG.

### Реестр источников

Для каждого файла:

- `source_id`;
- тип;
- название;
- ссылка или путь;
- дата;
- продукт;
- автор/чат, если известен;
- текст доступен или требуется транскрибация;
- статус обработки;
- hash.

### Извлечение из текстовых материалов

Из каждого пакета извлекать:

- реальные формулировки вопросов;
- опечатки и разговорные названия;
- повторяющиеся намерения;
- типовые follow-up;
- возражения;
- ожидаемый формат ответа;
- факты-кандидаты;
- ссылки на исходник.

В этом цикле главная ценность источников — не новые медицинские утверждения, а язык пользователей и карта реальных вопросов.

### Нормализация

- убрать персональные данные;
- дедуплицировать одинаковые сообщения;
- объединить смысловые повторы;
- сохранить 3-10 живых вариантов каждого вопроса;
- посчитать частоту;
- сопоставить с intent, entity и slot;
- неизвестное отправить в candidate queue.

### Публикация

Автоматически разрешено публиковать:

- новые тестовые формулировки;
- безопасные алиасы;
- связи вопрос -> существующий утвержденный ответ;
- технические clarification patterns;
- telemetry/gap-классификацию.

Требуют отдельного owner-решения:

- новая медицинская информация;
- изменение ограничений;
- изменение продающей карточки;
- новый claim;
- изменение цены;
- публикация отзыва как доказательства;
- изменение `OWNER_APPROVED_LOCKED`.

## 13. Автономный цикл улучшения

Создать единый runner:

`n8n/current/run_whieda_sql_quality_cycle.py`

Пример запуска:

```text
python run_whieda_sql_quality_cycle.py --source-batch <path> --cycles 5 --apply-safe
```

Runner должен сохранять состояние и уметь продолжить после сбоя.

### Цикл 1. Зафиксировать baseline

1. Экспортировать live workflow.
2. Сохранить hash ключевых узлов.
3. Запустить P0, feature и review smoke.
4. Зафиксировать метрики и текущие failures.
5. При красном P0 ничего не публиковать.

### Цикл 2. Взять пакет источников

1. Выбрать следующие 50-100 текстовых источников.
2. Проверить hash и не обрабатывать повторно.
3. Извлечь реальные вопросы и формулировки.
4. Обезличить.
5. Сохранить source lineage.

### Цикл 3. Построить кандидатов

1. Дедуплицировать вопросы.
2. Сгруппировать по смыслу.
3. Посчитать частоту.
4. Сопоставить с intent.
5. Сопоставить с товаром/сущностью.
6. Определить недостающий slot.
7. Сгенерировать вариации опечаток и коротких follow-up.

### Цикл 4. Проверить текущего бота

Каждый новый вопрос отправить на отдельном тестовом контексте либо в правильной последовательности.

Сохранить:

- фактический route;
- фактический SKU;
- текст;
- количество сообщений;
- фото;
- caption;
- latency;
- execution id.

### Цикл 5. Классифицировать провалы

Допустимые классы:

- `normalization_gap`;
- `alias_gap`;
- `intent_gap`;
- `entity_ambiguity`;
- `missing_slot`;
- `context_loss`;
- `priority_conflict`;
- `missing_answer`;
- `bad_answer_assembly`;
- `wrong_media`;
- `unexpected_dify`;
- `duplicate_output`;
- `unsafe_output`;
- `unsupported_scope`;
- `infrastructure_error`.

Нельзя чинить каждый вопрос отдельным `if`, если провал относится к общему паттерну.

### Цикл 6. Выбрать минимальное системное исправление

Порядок предпочтения:

1. нормализация;
2. алиас;
3. intent pattern;
4. priority;
5. slot/clarification;
6. context rule;
7. связь с существующим ответом;
8. новый утвержденный answer block;
9. изменение workflow.

### Цикл 7. Применить безопасные изменения

1. Обновить master-данные.
2. Запустить Sheet -> SQL sync.
3. Проверить sync audit.
4. Если нужен workflow patch — сначала export и backup.
5. Не менять owner-locked текст.

### Цикл 8. Прогнать тесты

Порядок:

1. тесты найденного паттерна;
2. затронутый domain suite;
3. P0;
4. full regression;
5. review smoke;
6. короткий group smoke, если менялась групповая ветка.

### Цикл 9. Решить судьбу изменения

Изменение остается, только если:

- новые кейсы прошли;
- P0 100%;
- regression не ухудшился;
- нет новых Dify-вызовов;
- latency не вышла за порог;
- нет дублей и неправильного SKU.

Иначе автоматически восстановить backup и зарегистрировать причину.

### Цикл 10. Отчет и следующий пакет

Сохранить:

- номер цикла;
- источники;
- добавленные вопросы;
- найденные паттерны;
- изменения;
- метрики до/после;
- rollback;
- открытые blockers.

Затем без ожидания пользователя перейти к следующему пакету.

## 14. Правила автономной работы

Агент не останавливается ради:

- выбора имени технической переменной;
- добавления теста;
- безопасного алиаса;
- исправления normalization;
- нового clarification pattern;
- отчета;
- backup;
- повторного запуска после временной ошибки.

Агент останавливается только при:

- необходимости изменить owner-locked контент;
- новом медицинском claim;
- цене без подтвержденного источника;
- миграции runtime;
- изменении credentials;
- необратимом удалении;
- трех последовательных инфраструктурных сбоях одного типа;
- падении P0, которое нельзя безопасно откатить.

При блокере агент продолжает независимые части работы и собирает один короткий список вопросов, а не прерывается после каждого файла.

## 15. Автоматические тестовые наборы

### P0

Не менее 30 критических кейсов:

- цена;
- PV;
- базовый/PRO;
- фото;
- видео;
- карточка;
- сравнение;
- ограничения;
- опечатка;
- контекст;
- приветствие;
- capabilities;
- Business FAQ;
- objection;
- отсутствие Dify.

### Corpus regression

Все реальные дедуплицированные вопросы. Цель к концу цикла: не менее 300 канонических вопросов и не менее 1000 формулировок.

### Mutation tests

Для каждого важного вопроса:

- опечатка;
- сокращение;
- перестановка слов;
- разговорный вариант;
- отсутствие названия товара при наличии контекста.

### Conversation tests

Не менее 50 последовательностей:

- карточка -> цена -> фото;
- карточка -> подробнее -> направление;
- базовый -> PRO -> сравнение;
- неполный запрос -> уточнение -> ответ;
- новый товар после старого контекста;
- два вопроса в одном сообщении.

### Negative tests

- неизвестный товар;
- бессмысленный текст;
- неподдерживаемая медицинская просьба;
- смешение бизнес-термина и товарного алиаса;
- битая ссылка;
- пустая ячейка;
- повтор Telegram update;
- повторный запуск sync.

## 16. Самодиагностика

Нужен ежедневный отчет:

- общее количество запросов;
- доля SQL;
- доля Dify;
- fallback rate;
- clarification rate;
- clarification success;
- топ неизвестных вопросов;
- топ нераспознанных слов;
- ошибки SKU;
- ошибки media;
- p50/p95 latency;
- sync status;
- количество новых и повторных gaps.

Critical alert:

- цена или SKU не найдены для известного товара;
- structured ушел в Dify;
- два фото;
- duplicate response;
- sync не выполнялся более 30 минут;
- P0 ниже 100%;
- fallback rate выше 5%.
