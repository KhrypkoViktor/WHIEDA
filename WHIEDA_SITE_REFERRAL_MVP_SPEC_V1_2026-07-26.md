# WHIEDA Site: Referral MVP

Версия: 1.0  
Дата: 2026-07-26  
Приоритет: P0, следующий релиз сайта  
Сайт: `https://whieda.sysarch.pro/`

## 1. Задача

Добавить к существующему сайту два режима реферальной персонализации без создания копий контента:

1. Анонимная ссылка `?ref=nnm`.
2. Именная ссылка `?ref=<partner_code>`.

После релиза Виктор должен сразу иметь возможность распространять:

`https://whieda.sysarch.pro/?ref=nnm`

Одновременно должна быть готова первая тестовая именная ссылка. Подключение следующего партнера должно выполняться добавлением одной записи в конфигурацию/таблицу, без копирования страниц и ручной переделки сайта.

## 2. Не менять

- Не менять основную концепцию, дизайн и тексты сайта без прямой необходимости.
- Не создавать второй сайт.
- Не копировать статьи и каталог.
- Не переносить сайт на другую платформу.
- Не переписывать весь frontend.
- Не добавлять авторизацию партнеров.
- Не строить полноценную CRM.
- Не менять основной SEO URL страниц.

## 3. Режимы

### 3.1. Обычный режим без `ref`

URL:

`https://whieda.sysarch.pro/`

Поведение остается текущим:

- показывается Виктор Хрипко;
- используется текущая фотография;
- работают текущие контакты;
- органическая заявка принадлежит Виктору;
- сайт остается его SEO-активом.

### 3.2. Анонимный режим `ref=nnm`

URL:

`https://whieda.sysarch.pro/?ref=nnm`

Назначение: партнерская/нейтральная ссылка без публичного имени консультанта.

Поведение:

- ref технически закрепляется за владельцем кода `nnm`;
- заявка и аналитика сохраняют `ref_code=nnm`;
- блок с фотографией, именем и личным представлением полностью скрывается;
- в шапке не показывается `Виктор Хрипко`;
- секция `Кто это разбирает` скрывается;
- в footer не показывается имя Виктора;
- прямой Telegram `@sunraysword` не показывается;
- персональные CTA заменяются нейтральными: `Задать вопрос`, `Получить консультацию`, `Оставить заявку`;
- заявка отправляется через общую форму и маршрутизируется по owner кода `nnm`;
- основной контент, каталог, статьи и цены не меняются;
- посетитель не видит технический ref-код и не обязан знать владельца ссылки.

Запрещен визуальный flash: при загрузке страницы сначала не должно появляться имя/фото Виктора, а затем исчезать.

### 3.3. Именной режим

Пример:

`https://whieda.sysarch.pro/?ref=ladnaya`

Поведение:

- подставляется имя партнера;
- подставляется его фотография;
- подставляется короткое описание;
- подставляются только разрешенные контакты;
- персональные CTA ведут к партнеру или в форму с его owner;
- заявка закрепляется за партнером;
- перед отправкой формы видно: `Ваш консультант — <Имя>`;
- пользователь явно понимает, кому будут переданы данные;
- во всех персональных блоках не остается имени, фотографии или Telegram Виктора;
- общий контент сайта не копируется и не меняется.

## 4. Конфигурация профилей

Не зашивать условные проверки `if ref === ladnaya` по разным компонентам.

Создать единый реестр профилей. Для MVP допустим локальный typed JSON/TS-файл. Структура должна позволять позже заменить его API/Postgres без изменения компонентов.

Пример логической схемы:

```ts
type ReferralProfile = {
  refCode: string;
  ownerId: string;
  displayMode: "anonymous" | "named";
  enabled: boolean;
  name?: string;
  photoUrl?: string;
  shortBio?: string;
  telegramUrl?: string;
  contactLabel?: string;
  tenantId: string;
};
```

Обязательные записи MVP:

```text
refCode: nnm
displayMode: anonymous
ownerId: viktor
tenantId: whieda
enabled: true
```

Первая именная запись:

```text
refCode: ladnaya
displayMode: named
tenantId: whieda
enabled: true после получения реальных данных
```

Для `ladnaya` нельзя выдумывать фотографию, контакт или биографию. Если данные еще не переданы, технический профиль и тесты подготовить, но публично не включать.

## 5. Определение и сохранение ref

Правила:

1. При открытии страницы прочитать `ref` из URL.
2. Нормализовать: lowercase, trim.
3. Разрешать только существующий активный код из реестра.
4. Не принимать имя, URL фотографии, Telegram или другой отображаемый текст непосредственно из query string.
5. Невалидный ref игнорировать и показывать обычный режим сайта.
6. Валидный ref сохранять в first-party cookie или localStorage на 30 дней.
7. Ref должен сохраняться при переходе между главной, каталогом, статьями и карточками.
8. Если пользователь открыл новую валидную ref-ссылку, отображать профиль из текущей ссылки.
9. Для заявки сохранять:
   - `first_ref`;
   - `active_ref`;
   - `owner_id`;
   - `tenant_id`.
10. `first_ref` после первой валидной атрибуции не переписывать молча.
11. Изменение владельца лида выполняется только backend-правилом и журналируется.

Для MVP owner заявки:

- если есть `first_ref`, использовать owner этого кода;
- иначе использовать текущий органический owner Виктора.

## 6. Персонализируемые элементы

Создать один referral context/store и использовать его во всех компонентах.

Проверить и подключить:

- подпись в шапке;
- hero/авторскую подпись, если содержит имя;
- секцию автора;
- фотографию;
- имя;
- short bio;
- CTA возле товаров;
- контактную форму;
- прямую Telegram-ссылку;
- footer;
- подписи `заказать через меня`;
- Open Graph только в пределах правил из раздела SEO.

Режим `anonymous`:

- персональный блок не занимает пустое место;
- секция удаляется из layout целиком;
- персональные CTA становятся нейтральными;
- скрытые данные не должны оставаться в доступных `alt`, `aria-label`, title или видимом DOM.

Режим `named`:

- сохраняет аккуратную верстку при коротком и длинном имени;
- фотография имеет стабильное соотношение сторон;
- при отсутствии необязательного bio блок не ломается;
- контакт показывается только если разрешен в профиле.

## 7. Форма заявки

Текущую форму сохранить и дополнить скрытыми серверно проверяемыми полями:

- `ref_code`;
- `first_ref`;
- `active_ref`;
- `owner_id`;
- `tenant_id`;
- `landing_url`;
- `current_url`;
- `utm_source`;
- `utm_medium`;
- `utm_campaign`;
- timestamp.

Нельзя доверять `owner_id`, который пришел только с frontend. Backend повторно сопоставляет `ref_code` с allowlist/реестром.

В именном режиме перед кнопкой:

```text
Заявка будет передана: <Имя партнера>
```

В анонимном режиме:

```text
Заявка будет передана консультанту WHIEDA.
```

После отправки:

- пользователь видит понятный success state;
- повторный клик не создает дубль;
- ошибка не очищает введенные поля;
- событие и ошибка логируются без утечки контакта в публичную аналитику.

## 8. Доставка заявки

Переиспользовать текущий канал формы, если он работает.

Минимальный payload для Telegram/CRM:

```text
Новая заявка #<id>
Ref: <ref_code или organic>
Владелец: <owner>
Источник: <страница>
Интерес: <тип>
Статус: новая
```

Контакт и сообщение пользователя должны видеть только владелец лида и уполномоченный admin.

Если общей Telegram-группы лидов пока нет:

- не блокировать frontend-релиз;
- сохранить ref-поля в текущей доставке;
- отдельно зафиксировать точку подключения группы;
- не имитировать успешную отправку, если backend реально не принял форму.

## 9. SEO

Все варианты одной страницы с `ref` имеют canonical без query-параметров.

Пример:

```html
<link rel="canonical" href="https://whieda.sysarch.pro/catalog/aktivator">
```

Требования:

- `ref`, `utm_source`, `utm_medium`, `utm_campaign` не входят в canonical;
- sitemap содержит только основные URL без ref;
- для Яндекса настроить `Clean-param` для referral и UTM-параметров;
- ref-страницы не создаются как отдельные статические HTML-копии;
- персонализация не меняет основной текст статьи;
- structured data статьи/товара остается общей;
- имя партнера не подмешивается в SEO title/description основной статьи;
- именные и анонимные варианты не должны конкурировать с основной страницей.

Open Graph для MVP оставить нейтральным и общим. Не генерировать отдельные индексируемые OG-страницы под каждого партнера.

## 10. Безопасность и приватность

- Ref-код работает только через allowlist.
- Экранировать любые данные профиля.
- Не загружать произвольные удаленные изображения из query string.
- Telegram bot token отсутствует во frontend bundle.
- Backend endpoint имеет rate limit и антиспам.
- Контакты пользователя не попадают в URL, логи аналитики и client errors.
- Фотография и публичные данные партнера включаются только после его согласия.
- Должна существовать возможность немедленно отключить ref-профиль.
- Отключенный ref переводит сайт в обычный режим и не ломает страницу.

## 11. Аналитика

Добавить события без персональных данных:

- `ref_visit`;
- `ref_cta_click`;
- `ref_form_start`;
- `ref_form_submit_success`;
- `ref_form_submit_error`.

Параметры:

- `ref_code`;
- `display_mode`;
- `owner_id`;
- `tenant_id`;
- path;
- UTM.

Не передавать имя, телефон, Telegram пользователя или текст сообщения в систему веб-аналитики.

## 12. Первый именной профиль

Подготовить профиль `ladnaya`.

Для окончательного включения запросить у Виктора только:

1. Точное публичное имя.
2. Фотографию.
3. Telegram/contact URL.
4. Короткое описание до 300 символов.
5. Подтверждение согласия партнера на публикацию.

До получения этих данных:

- весь механизм реализовать;
- использовать профиль только в локальном/dev preview;
- не публиковать выдуманные данные;
- `nnm` выпустить независимо.

## 13. Тесты

### P0

1. Обычный URL показывает текущий сайт Виктора.
2. `?ref=nnm` нигде визуально не показывает имя Виктора.
3. `?ref=nnm` не показывает фотографию Виктора.
4. `?ref=nnm` не показывает `@sunraysword`.
5. Анонимный CTA и форма работают.
6. Именной ref показывает правильное имя, фото и контакт.
7. Именной ref не оставляет персональных данных Виктора.
8. Невалидный ref безопасно показывает обычный режим.
9. Ref сохраняется после перехода в каталог и обратно.
10. Ref сохраняется после reload.
11. Форма передает правильный ref и owner.
12. Backend не доверяет подмененному owner из frontend.
13. Повторная отправка не создает дубль.
14. Canonical не содержит query.
15. Sitemap не содержит ref.

### Viewports

Проверить:

- 360x800;
- 390x844;
- 768x1024;
- 1440x900.

На каждом viewport:

- нет пустого места после скрытия блока;
- имя не вылезает за контейнер;
- CTA доступен;
- форма не перекрывается;
- нет flash персональных данных.

## 15. Definition of Done

Задача готова, когда:

- ссылка `https://whieda.sysarch.pro/?ref=nnm` безопасна для рассылки;
- персональные данные Виктора в режиме `nnm` полностью скрыты;
- заявка из `nnm` реально доставляется с правильной атрибуцией;
- обычный сайт без ref не изменился;
- первая именная ссылка работает после одной конфигурационной записи;
- ref сохраняется по сайту;
- SEO URL и canonical не размножаются;
- мобильная версия проверена;
- есть тесты и rollback;
- следующий партнер подключается без изменения компонентов.
