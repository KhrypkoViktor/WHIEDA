# WHIEDA: RAG, глубокие ответы и живая модель к демо

Дата: 2026-07-14  
Статус: архитектурное решение и исполняемое ТЗ

Правила формулировок, доступа и будущей монетизации: `WHIEDA_COMPLIANCE_SELLING_LANGUAGE_ACCESS_MONETIZATION_RB_2026-07-14.md`.

## 1. Решение: две коробки знаний и живой собеседник

### Коробка 1. SQL: 90% повседневных вопросов

SQL содержит не только короткие карточки. В него переносим все знания, которые можно заранее разложить по понятным темам и дать без свободного рассуждения модели:

- короткие карточки;
- расширенные разделы по товару;
- применения и готовые сценарии;
- правила и протоколы;
- ограничения;
- FAQ;
- ссылки на документы, презентации, фото и видео;
- утвержденные паттерны из отзывов.

Сто ссылок или сотни готовых текстовых блоков для SQL не являются проблемой. Ответ остается быстрым, дешевым и контролируемым.

### Коробка 2. RAG: те же знания с гибким пониманием вопроса

RAG содержит полные и расширенные версии утвержденных материалов. Он нужен не потому, что SQL не вмещает данные, а когда:

- человек формулирует вопрос странно или длинно;
- в одном сообщении несколько связанных вопросов;
- нужен индивидуально собранный ответ из нескольких разделов;
- нужен пересказ документа своими словами;
- важен контекст нескольких сообщений;
- точного готового SQL-ответа нет, но ответ есть внутри библиотеки.

RAG и SQL не должны противоречить друг другу. Они строятся из одного реестра источников и одной системы статусов проверки.

### Живой собеседник: выход за рамки базы

Отдельный маршрут умеет:

- поддержать разговор;
- объяснить общий термин;
- посочувствовать или мотивировать;
- помочь сформулировать вопрос;
- рассуждать, явно отделяя вывод модели от фактов WHIEDA;
- по отдельной команде искать информацию в интернете.

Он не имеет права придумывать факты о товарах, цены, протоколы и медицинские обещания.

## 2. Четыре маршрута ответа

WHIEDA использует не один способ ответа, а четыре маршрута.

### Уровень A. Быстрый ответ

- Источник: structured SQL.
- Для чего: карточка, цена, PV/W$, фото, видео, короткое применение, ограничения, сравнение товаров.
- Модель не вызывается.
- Цель по времени: до 2 секунд.

### Уровень B. Ответ по внутренней библиотеке

- Источник: векторный поиск по утвержденным материалам.
- Для чего: подробное применение, методики, устройство, механизм, презентации, научные материалы, история продукта.
- Модель получает только 3-5 подходящих фрагментов, а не весь файл и не всю библиотеку.
- Каждый ответ показывает тип источника и дает ссылку на оригинал.
- Цель по времени: 3-8 секунд.

### Уровень C. Живой ответ модели

- Источник: общие знания модели, без выдачи их за материалы WHIEDA.
- Для чего: разговор, объяснение терминов, помощь сформулировать вопрос, общие немедицинские темы.
- Ответ явно помечается: `Общий ответ модели, не из базы WHIEDA`.
- Внутренние факты о товарах модель не придумывает и берет только из SQL/RAG.

### Уровень D. Глубокий разбор с интернетом

- Запускается только явно: кнопка/команда `Проверить в интернете` или `Глубокий разбор`.
- Совмещает внутренние источники, сильную модель и поиск в интернете.
- Ответ разделяет: что найдено в базе WHIEDA, что найдено во внешних источниках, какой вывод сделала модель.
- Для медицинских тем не ставит диагноз и не превращает исследование технологии в доказательство эффективности конкретного товара.
- Доступ и частота ограничиваются, потому что это самый дорогой и медленный маршрут.

## 3. Что хранится где

### Google Drive

Хранит оригиналы:

- PDF и презентации;
- инструкции и методички;
- научные статьи;
- текстовые отзывы;
- видеоотзывы и обучающие видео.

Тяжелый оригинальный файл не нужно помещать в векторную базу. Пользователь получает ссылку на Drive, если хочет открыть оригинал.

### Векторная база

Хранит только подготовленный текст и метаданные:

- маленькие смысловые фрагменты;
- заголовок и раздел;
- товар;
- направление ответа;
- тип и уровень надежности источника;
- статус проверки;
- `source_id`;
- ссылка на исходный файл;
- страница PDF или таймкод видео, если доступны.

Большое количество проиндексированных материалов не означает большой расход токенов на каждый вопрос. В модель передаются только найденные фрагменты.

### SQL

Хранит:

- утвержденные короткие ответы;
- товары, алиасы, цены и ресурсы;
- готовые разделы `Подробнее`;
- индекс источников;
- статусы обработки и проверки;
- популярные вопросы и кэш уже собранных ответов.

### Новая вкладка structured master: `Product_Details`

Одна строка = один готовый смысловой блок по одному товару.

Обязательные поля:

- `detail_id`;
- `project_id`;
- `sku`;
- `canonical_name`;
- `section`: `usage`, `use_case`, `protocol`, `mechanism`, `safety`, `experience`, `science`, `faq`;
- `topic`: конкретная тема внутри раздела;
- `question_aliases`: типичные формулировки пользователя;
- `answer_short`: быстрый ответ;
- `answer_full`: подробный structured-ответ;
- `source_ids`: ссылки на записи `Resource_Links`;
- `source_class`: `official_instruction`, `company_training`, `presentation`, `study`, `testimonial`, `owner_note`;
- `evidence_status`: `verified`, `manufacturer_claim`, `reported_experience`, `unverified`;
- `review_status`: `approved`, `needs_business_review`, `needs_medical_review`, `blocked`;
- `audience`: `public`, `partner`, `leader`, `admin`;
- `priority`;
- `active`;
- `updated_at`.
- `owner_state`;
- `content_hash`;
- `publication_scope`.

Runtime берет только `active=true` и `review_status=approved`. Остальные строки можно хранить, но нельзя показывать пользователю.

Исключение для уже утвержденного владельцем текста: агент не переписывает его при изменении правил. Он создает отдельное предложение и оставляет live-текст неизменным до решения Виктора.

### Новая вкладка Content Factory: `Knowledge_Drafts`

Сюда складывается нарезанное сырье до проверки. Поля повторяют `Product_Details` и дополнительно содержат:

- `raw_text`;
- `source_fragment`;
- `page_or_timecode`;
- `risk_flags`;
- `review_comment`;
- `reviewed_by`;
- `reviewed_at`.

После утверждения строка копируется/синхронизируется в `Product_Details`. Content Factory остается рабочим цехом, structured master становится источником готовых ответов.

### Существующая вкладка `Resource_Links`

Не создавать новую таблицу ссылок. Расширять существующую при необходимости. Она хранит документы, PDF, презентации, фото, исследования и видео. Для каждого ресурса нужен стабильный `resource_id`, который используется в `Product_Details` и RAG.

## 4. Направления ответа `Подробнее`

После `Подробнее` бот не повторяет карточку. Он показывает выбор:

1. `Как использовать`.
2. `Для каких ситуаций смотрят`.
3. `Опыт людей`.
4. `Как это работает`.
5. `Исследования`.
6. `Материалы и видео`.

Для каждого товара SQL хранит наличие каждого раздела. Бот не предлагает пустую кнопку.

## 5. Приоритет источников

1. Официальная инструкция: применение и ограничения.
2. Проверенный внутренний материал: сведения о конкретном товаре.
3. Научная статья: только то, что в ней действительно исследовалось.
4. Отзывы: только опыт конкретных людей, не медицинское доказательство.
5. Презентация: маркетинговое объяснение, не доказательство.
6. Интернет и общие знания модели: отдельный внешний слой.

При конфликте бот показывает, что источники расходятся, и не склеивает их в уверенный факт.

## 6. Конвейер 800 видео и файлов

Не пересматривать все материалы вручную до машинной обработки.

### Шаг 1. Реестр

Для каждого исходника создать запись:

- стабильный `source_id`;
- имя файла;
- Drive file id и URL;
- тип: отзыв, обучение, презентация, инструкция, статья;
- дата и автор, если известны;
- товар/тема, если известны;
- hash для поиска дублей;
- статус обработки.

### Шаг 2. Расшифровка

- Из видео извлечь речь и сделать транскрипт.
- Транскрипт назвать по `source_id`.
- В начало транскрипта записать `source_id`, имя исходника и Drive URL.
- Для полезных фрагментов сохранять таймкоды.

Так NotebookLM или другая модель всегда сможет связать вывод с конкретным роликом.

### Шаг 3. Машинная сортировка

Из каждого материала извлекать:

- товары;
- ситуацию/запрос человека;
- как использовал;
- что человек сообщил о результате;
- срок;
- ограничения и побочные наблюдения;
- полезную цитату;
- качество и полноту материала.

### Шаг 4. Дедупликация и кластеры

- Удалить точные дубли.
- Сгруппировать похожие рассказы.
- Посчитать повторяющиеся сценарии.
- Не превращать частое повторение в доказанный медицинский факт.

### Шаг 5. Проверка человеком

- Для первичной проверки показывать не 800 видео, а кластеры и лучшие 1-3 примера каждого сценария.
- Бизнес проверяет понятность, ценность и соответствие реальному опыту.
- Врач проверяет медицинские формулировки и ограничения.
- После проверки материал получает статус `approved`, `restricted`, `rejected` или `needs_review`.

### Шаг 6. Публикация

- Повторяющиеся утвержденные паттерны идут в SQL как готовый быстрый ответ.
- Полные транскрипты и подробности идут в векторную базу.
- Исходное видео остается на Drive и отдается ссылкой.

## 7. Экономия стоимости и времени

- Не вызывать модель для structured-запросов.
- Не передавать модели целые PDF и длинные транскрипты на каждый вопрос.
- Ограничить retrieval 3-5 небольшими фрагментами.
- Сначала фильтровать по товару, типу материала и статусу проверки.
- Для обычного RAG использовать быструю недорогую модель.
- Сильную модель и интернет запускать только явно.
- Кэшировать повторяющиеся глубокие вопросы и утвержденные ответы.
- Логировать для каждого ответа маршрут, модель, токены, задержку и источники.
- Индексировать только новые или измененные файлы, а не весь архив заново.

### Выбор моделей

- `Gemini 3.1 Flash-Lite` stable: классификация, извлечение структуры, маршрутизация и массовая обработка архива.
- `Gemini 3.5 Flash` stable: обычные RAG-ответы и живой разговор.
- Интернет-поиск через Gemini Search Grounding: только уровень D и только по явному запросу.
- Не использовать preview/latest alias в prod, если доступна фиксированная stable-модель.
- Перед окончательным включением прогнать один и тот же контрольный набор на текущей модели Dify и двух Gemini-моделях; сравнить качество, медиану задержки и цену.

## 8. Пример разбора переданного текста Активатора

Переданный материал нельзя публиковать одним массивом. Его разложить так:

### Механизм

Утверждения про `спящие клетки`, глубину 10-14 см, совпадение частот здоровых клеток, нагрев изнутри и квантовую фокусировку:

- сохранить в `Knowledge_Drafts`;
- статус `needs_medical_review` или `needs_business_review`;
- класс `manufacturer_claim` или `unverified`;
- не использовать публично до появления точного источника и проверки.

### Инструкция и безопасность

Вода 50-60 градусов, точные объемы, час в сутки, паузы, режимы, озон PRO, противопоказания:

- привязать к официальной инструкции или обучающему материалу;
- точные цифры публиковать только после сверки источника;
- ограничения проверяет врач;
- после утверждения перенести в `Product_Details` с section `usage` и `safety`.

### Общий протокол

Пять шагов, распределение времени, движения прибором, отдых после процедуры:

- section `protocol`;
- аудитория по умолчанию `partner`;
- источник и версия обязательны;
- до проверки хранить как `needs_business_review` и `needs_medical_review`.

### Протоколы по конкретным состояниям

Варикоз, лимфостаз, лимфоузлы, боли, гинекология и грудные железы:

- не публиковать автоматически;
- разобрать в `Problem_Solution_Matrix`;
- обязательный medical review;
- публичный ответ не должен подменять диагноз или назначение.

### Реакции после процедур

Фразы про `целительный криз`, нормальность температуры, давления, тошноты, диареи и других симптомов:

- статус `blocked` до медицинского разбора;
- нельзя автоматически объяснять опасный симптом детоксикацией или недостатком воды;
- после проверки разделить допустимые бытовые реакции и safety-trigger.

## 9. Что показать на демо

Подготовить качественный RAG-набор только для 2-3 товаров. Не ждать обработки всего архива.

### Демонстрация 1. Внутренняя библиотека

1. Запросить карточку товара: быстрый SQL.
2. Нажать `Подробнее` -> `Как использовать`.
3. Получить гибкий ответ из инструкции с названием источника и ссылкой.
4. Спросить: `Откуда это взялось?` и получить точный документ/страницу.

### Демонстрация 2. Опыт людей

1. Спросить, как люди используют товар в определенной ситуации.
2. Получить 2-3 повторяющихся сценария с формулировкой `люди сообщали`.
3. Получить ссылки на конкретные текстовые или видеоотзывы.

### Демонстрация 3. Механизм и исследования

1. Попросить простое объяснение технологии.
2. Затем попросить глубже.
3. Ответ должен разделить материалы производителя и научные источники.

### Демонстрация 4. Живая модель

1. Задать общий вопрос вне каталога.
2. Бот отвечает как живая модель и явно сообщает, что ответ не взят из базы WHIEDA.
3. По явной команде выполняет интернет-поиск и показывает внешние источники.

## 10. Порядок реализации

1. Создать `Knowledge_Drafts` в Content Factory.
2. Нарезать переданный текст Активатора на строки с рисками и источниками.
3. Создать `Product_Details` в structured master.
4. Перенести туда только утвержденные строки.
5. Дополнить существующий `Resource_Links` документами, презентациями и видео Активатора.
6. Добавить `Product_Details` и `Resource_Links` в 15-минутную синхронизацию Google Sheet -> SQL.
7. Реализовать structured `Подробнее` из SQL.
8. Проверить текущий Dify dataset и live retrieval на 5 контрольных вопросах.
9. Ввести в RAG те же `source_id`, разделы, статусы и аудитории.
10. Подготовить 10-20 надежных документов по 2-3 товарам.
11. Реализовать router: SQL -> RAG -> живая модель -> явный интернет.
12. Добавить ссылки/страницы/таймкоды в ответы RAG.
13. Добавить кэш, лимиты и telemetry стоимости.
14. Собрать минимум 20 тестов: правильный маршрут, источник, отсутствие выдумок, время и стоимость.

## 11. Критерий готовности

- `Подробнее` не повторяет карточку;
- бот отвечает минимум по четырем внутренним направлениям для 2-3 демо-товаров;
- каждый RAG-ответ связан с конкретным источником;
- отзывы не выдаются за медицинские факты;
- модель явно отделяет внутреннюю базу, собственный общий ответ и интернет;
- SQL-ответы остаются быстрыми и не используют LLM;
- обычный RAG укладывается в целевое время 3-8 секунд;
- для каждого теста видны маршрут, задержка и расход токенов;
- повторный популярный вопрос может обслуживаться из кэша.
