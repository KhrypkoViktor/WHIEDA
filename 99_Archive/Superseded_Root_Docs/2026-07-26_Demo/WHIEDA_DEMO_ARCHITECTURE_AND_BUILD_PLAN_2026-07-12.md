# WHIEDA: архитектурные решения и план разработки к демо

Дата: 2026-07-12  
Статус: согласовано к реализации  
Исполнитель: следующая сильная модель  
Горизонт: ближайшие 1-2 рабочих дня, затем подготовка демонстрации

Этот файл является главным заданием на ближайший цикл. Старые roadmap-файлы использовать только как историю. Если старый документ противоречит этому плану, действует этот план.

## 1. Цель демо

Показать не просто Telegram-бота, а ядро цифрового советника, которое:

- мгновенно и дешево отвечает на частые вопросы из SQL;
- выдает корректное фото товара прямо в Telegram;
- удерживает контекст короткого follow-up;
- дает более глубокий ответ только когда он действительно нужен;
- собирает замечания доверенных экспертов;
- превращает замечания в управляемую очередь задач;
- показывает, что было исправлено и проверено;
- готово принимать большой массив реальных отзывов без смешивания опыта людей с медицинскими фактами.

Главный эффект демо: система уже работает, умеет учиться и имеет понятный путь масштабирования.

## 2. Неподвижные архитектурные решения

### 2.1. Контур

- Текущий сервер и текущий `advisor-whieda-phase1` считаются единственным `prod`.
- Текущий runtime Postgres остается рабочей базой.
- Supabase сейчас не является ядром и миграцию на него не начинать.
- Перед каждым live-изменением обязательно делать export текущего workflow и фиксировать active version.
- Изменения вносить аддитивно. Не удалять старые колонки, узлы и данные до отдельного этапа очистки.

### 2.2. Уровни ответа

Ответ строится по каскаду от самого дешевого и точного уровня к дорогому:

1. `L0 Structured` — SQL без LLM: цена, PV, W$, SKU, алиасы, фото, ссылки, короткие утвержденные поля.
2. `L1 Composer` — шаблонная сборка из SQL: короткая карточка, цена + фото, правила использования, ограничения. LLM не должна придумывать факты.
3. `L2 RAG` — Dify для длинных объяснений, механизмов, обучающих материалов и вопросов, которых нет в structured слое.
4. `L3 Deep` — сильная модель только для сложного синтеза: сравнение нескольких источников, разбор неоднозначного запроса, подготовка проекта ответа эксперту. Доступ ограниченный.
5. `Safety gate` — проверка медицинских и доходных обещаний перед отправкой независимо от уровня ответа.

Правило маршрутизации: если L0 или L1 уверенно закрывает запрос, Dify и глубокую модель не вызывать.

### 2.3. Источники правды

- Товары, цены, PV, W$, алиасы, карточки, фото и ссылки: structured master и runtime SQL.
- Длинные знания и объяснения: Dify/RAG.
- Рабочие замечания и задачи: `advisor_review_queue`.
- Сырые отзывы: Google Drive как неизменяемый raw-источник, не RAG и не Product Cards напрямую.
- Медицинское утверждение становится утвержденным только после medical review.
- Бизнес-формулировка становится утвержденной только после business review.

### 2.4. Медиа

- Фото отправлять через Telegram `sendPhoto`.
- PDF и презентации пока отдавать аккуратной ссылкой.
- `sendDocument` до демо не делать.
- На один запрос пользователя отправлять одно фото и один ответ. Дубли являются runtime bug.

### 2.5. Review loop

- Один inbox: `advisor_review_queue`.
- Замечания принимаются обычным языком, обязательных меток `ВРАЧ:` или `БИЗНЕС:` нет.
- `@SunRaySword` — `super_admin`, `@OnlineElena` — `business`.
- Замечание trusted reviewer сразу становится рабочим.
- Замечание другого пользователя сохраняется как `candidate` и не меняет знания автоматически.
- Никакое замечание не должно автоматически менять prod-данные.
- Автоматизация может классифицировать, назначать owner/priority, предлагать исправление и запускать тест. Применение фактов и медицинских формулировок требует подтверждения.

## 3. Целевая схема review queue

Перевести операционные поля из `source_payload` в явные колонки аддитивной миграцией V03:

- `source_ref` — стабильный уникальный идентификатор;
- `source_type` — telegram, runtime, smoke_test, import;
- `trust_level` — trusted, candidate;
- `review_type` — knowledge_gap, answer_error, medical_review, business_voice_review, media_issue, structured_data_issue, runtime_bug, content_task;
- `target_layer` — products_prices, product_aliases, product_cards, resource_links, solution_bundles, mechanism_explainers, problem_solution_matrix, marketing_plan, voice_rules, medical_safety, dify_knowledge, n8n_workflow, sql_runtime, testimonials;
- `priority` — high, medium, low;
- `owner` — super_admin, business, medical, admin, content, dev;
- `queue_status` — pending, triage, approved, in_work, applied, verified, closed, rejected, duplicate;
- `user_text`, `bot_answer`, `feedback_text`, `suggested_fix`;
- `taken_by`, `taken_at`, `closed_by`, `closed_at`;
- `created_at`, `updated_at`;
- `source_payload` — оставить для исходного контекста и обратной совместимости.

Требования:

- существующие записи backfill из `source_payload`;
- старый `status` не ломать;
- повторная запись с тем же `source_ref` не создает дубль;
- action-команды после миграции работают через явные поля;
- до переключения workflow проверить структуру и данные read-only запросами;
- предусмотреть rollback переключения workflow без rollback данных.

## 4. Архитектура отзывов

Тысячи текстовых и видеоотзывов — отдельный ценный слой `Testimonials`, но не медицинская база фактов.

Источник:

- отзывы лежат на Google Drive;
- точную папку Виктор передаст перед началом обработки;
- до этого папки и файлы отзывов самостоятельно не искать;
- оригиналы на Drive не переименовывать, не перемещать и не изменять.

Для первичного анализа большого массива использовать NotebookLM:

- загружать туда логические партии источников, а не весь архив одной кучей;
- получать темы, повторяющиеся пользовательские сигналы, вопросы, формулировки и кандидаты в бандлы;
- требовать привязку каждого вывода к исходным фрагментам;
- выгружать результат в структурированный промежуточный формат;
- вывод NotebookLM считать аналитическим черновиком, а не источником медицинских фактов;
- дальше пропускать выводы через medical/business review и только затем публиковать в рабочие слои.

### 4.1. Что хранить

- исходный текст или расшифровку без редактирования;
- ссылку/идентификатор исходного сообщения или видео;
- дату и продукт;
- проблему словами автора;
- наблюдаемый результат словами автора;
- длительность использования, если указана;
- совместно использованные продукты;
- нежелательные реакции, если указаны;
- извлеченные claims;
- статус проверки;
- разрешение на публичное использование, если известно;
- обезличенную публичную версию.

### 4.2. Статусы утверждений

- `raw_claim` — личное утверждение автора;
- `pattern` — повторяющийся мотив в нескольких независимых отзывах;
- `medical_review_required` — формулировка требует врача;
- `approved_as_experience` — можно говорить только как об опыте людей;
- `approved_medical_wording` — врач одобрил допустимую формулировку;
- `rejected` — нельзя использовать;
- `needs_source` — не хватает исходника или контекста.

### 4.3. Главное правило

Даже 50 одинаковых отзывов не доказывают лечение. Они доказывают повторяющийся пользовательский сигнал. Система может сказать: «В отзывах люди часто упоминают...», но не «продукт лечит...», пока нет отдельного подтвержденного основания.

### 4.4. Как использовать

- находить реальные слова клиентов и алиасы;
- выявлять частые вопросы и проблемы;
- формировать кандидаты для `Problem_Solution_Matrix`;
- предлагать идеи бандлов;
- усиливать Product Cards живыми сценариями;
- готовить врачу сгруппированные claims на проверку;
- выдавать утвержденные обезличенные кейсы по запросу;
- строить приоритет контента по частоте реальных запросов.

До демо сделать схему импорта и небольшой показательный набор. Не загружать весь массив вслепую в Dify.

## 5. План реализации: шесть вех

### Веха 1. Нормализовать review queue

Реализовать:

- проверить фактическую live-схему;
- довести `WHIEDA_review_queue_schema_V03.sql` до полностью аддитивной миграции;
- сделать backfill;
- создать views: actionable, candidates, stats;
- переключить `/review_next`, `/review_take`, `/review_close` на явные поля;
- добавить `/review_apply` и `/review_verify`;
- ограничить action-команды trusted users;
- оставить совместимость со старым payload.

Критерий готовности:

- trusted-замечание проходит `pending -> in_work -> applied -> verified -> closed`;
- candidate не попадает в работу без повышения;
- после повторной команды нет дубля;
- текущие read-only команды продолжают работать.

### Веха 2. Встроить наблюдение и реальные тесты

Создать единый smoke pack, который запускается перед и после каждого live-патча.

Обязательные группы:

- 5 запросов цены/повторки/первички;
- 5 запросов фото и проверка ровно одного `sendPhoto`;
- 5 карточек и follow-up `а сколько?`, `дай фото`, `подробнее`;
- 5 замечаний trusted/candidate;
- 3 medical safety запроса;
- 3 business/voice запроса;
- 3 runtime failure cases: SQL timeout, Dify timeout, Telegram error.

Каждый тест сохраняет:

- вход;
- выбранный route;
- источники ответа;
- вызван ли LLM;
- время ответа;
- количество Telegram messages/photos;
- итог success/fail;
- execution id;
- созданный gap при ошибке.

Добавить автоматические детекторы:

- дубль ответа или фото;
- пустой ответ;
- неверный route;
- structured-вопрос ушел в Dify;
- ссылка не открывается;
- цена без найденного SKU;
- fallback повторяется выше порога;
- execution завершился ошибкой.

Критерий готовности:

- один запуск дает короткий отчет pass/fail;
- тест не пишет мусор в рабочую очередь;
- реальные ошибки автоматически создают `runtime_bug` или нужный тип review item.

### Веха 3. Закрыть демонстрационный structured/media слой

Выбрать топ-10 товаров и для каждого обеспечить:

- каноническое название и SKU;
- алиасы;
- первичную и повторную цену;
- PV/W$, если существуют;
- короткую карточку;
- способ применения;
- ограничения только из утвержденного источника;
- одно основное фото;
- рабочие ссылки на материалы;
- follow-up context.

Обязательные алиасы цены:

- `партнерская`, `повторка`, `повторная покупка` — один тип цены;
- `основная`, `первичка`, `розничная`, `цена при регистрации` — один тип цены.

Проверить в личке и реальной группе:

- фото не дублируется;
- ответ не задерживается из-за ненужного Dify;
- `дай фото`, отправленное сразу после карточки, понимает товар из контекста;
- неизвестный товар создает gap и не выдумывает ответ.

Критерий готовности:

- все демонстрационные запросы проходят smoke pack;
- один вопрос вызывает один ожидаемый route;
- structured-ответ не расходует токены LLM.

### Веха 4. Сделать Testimonials MVP

Реализовать pipeline `Google Drive -> NotebookLM -> structured staging -> review`:

1. после передачи точной папки построить read-only manifest источников;
2. разбить материалы на партии по теме/товару/источнику для NotebookLM;
3. сохранить Drive file id и ссылку на исходник;
4. получить из NotebookLM структурированные themes/claims/questions/patterns с цитатами на источники;
5. нормализовать результат и удалить логические дубли в staging;
6. связать упоминания с товарными алиасами;
7. создать medical/business review items;
8. сформировать читаемый пакет на проверку;
9. публиковать в рабочие слои только approved records.

Видео на первом проходе:

- не скачивать все видео без необходимости;
- сохранить Drive file id и связь с сообщением;
- использовать существующий текст сообщения/подпись;
- транскрибировать только выбранные файлы из демонстрационной выборки;
- транскрипт хранить как производный артефакт с привязкой к оригинальному file id.

Для демо использовать небольшой реальный набор: 30-100 отзывов по 2-3 товарам. Показать путь от сырого экспорта до повторяющихся тем и задач врачу/бизнесу.

Критерий готовности:

- исходник всегда доступен;
- любая сводка трассируется до отзывов;
- медицинские claims не попадают в Product Cards автоматически;
- дубли не увеличивают частоту;
- персональные данные не показываются в публичном ответе.

### Веха 5. Зафиксировать маршрутизатор уровней памяти

Ввести явный route result до генерации ответа:

- `intent`;
- `entities` и найденный product id;
- `answer_level` L0/L1/L2/L3;
- `sources`;
- `confidence`;
- `safety_flags`;
- `context_ref`;
- `fallback_reason`;
- `token_budget`.

Правила:

- цена, фото, ссылка, SKU, PV, W$ всегда начинают с L0;
- короткая карточка начинается с L1;
- механизм и длинное обучение идут в L2;
- L3 вызывается только отдельным условием сложности или ролью пользователя;
- при низкой уверенности не смешивать случайные продукты, а уточнить вопрос или создать gap;
- результат каждого route писать в telemetry без полного дублирования чувствительных данных.

Критерий готовности:

- по execution видно, почему выбран уровень;
- можно посчитать долю запросов, закрытых без LLM;
- Dify timeout не ломает L0/L1;
- follow-up сохраняет последний product/topic с ограниченным TTL.

### Веха 6. Собрать демонстрационный сценарий и панель состояния

Сделать короткий сценарий на 8-10 минут:

1. вопрос о товаре — короткая карточка;
2. `а сколько стоит повторка?` — точная цена из SQL;
3. `дай фото` — одно корректное фото;
4. сложный вопрос — переход к глубокому ответу;
5. Елена пишет обычное замечание к ответу;
6. замечание автоматически классифицируется и появляется в очереди;
7. показать `/review_next business` и жизненный цикл задачи;
8. показать анализ небольшой пачки отзывов;
9. показать smoke report и долю ответов без LLM.

Подготовить резервный prerecorded/probe набор на случай нестабильного Telegram или внешнего API. Это не подмена live-демо, а страховка показа.

Критерий готовности:

- сценарий дважды подряд проходит без ручной починки;
- все демонстрационные данные реальные и проверенные;
- нет медицинских обещаний;
- есть короткие цифры: latency, pass rate, SQL/no-LLM rate, open review items.

## 6. Порядок работы исполнителя

Работать строго в этом порядке:

1. Сделать read-only снимок live workflow, active version и live DB schema.
2. Довести и локально проверить миграцию review queue.
3. Сделать backup и применить миграцию.
4. Переключить action-команды и прогнать regression.
5. Собрать smoke runner и telemetry checks.
6. Закрыть топ-10 structured/media сценариев.
7. Сделать Testimonials MVP на малой выборке.
8. Ввести явный route result и метрики стоимости.
9. Собрать demo runbook и провести два полных прогона.
10. После каждой вехи обновлять один live-status файл, а не создавать новый отчет на каждый шаг.

Не переходить к следующей вехе, пока критерии текущей не выполнены или проблема явно не записана как blocker.

## 7. Обязательные правила изменения prod

- Не редактировать live вслепую через UI.
- Сначала export/backup, потом локальный patch, validation, publish, readback.
- Никогда не считать publish успешным только по HTTP 200: проверять active version и live execution.
- Не тестировать Telegram на несуществующих chat id.
- Не печатать credentials в логи и артефакты.
- Не менять Dify, если задача закрывается SQL/n8n.
- Не мигрировать в Supabase в этом цикле.
- Не делать destructive schema changes.
- При падении вернуть workflow на предыдущую active version, данные миграции не удалять.
- Любой исправленный баг закрепить регрессионным тестом.

## 8. Что не делать к демо

- полный `Problem_Solution_Matrix` до врачебной проверки;
- автоматическую медицинскую консультацию;
- автоматическое применение пользовательских замечаний;
- массовую загрузку сырых отзывов в Dify;
- `sendDocument`;
- mini app;
- MCP в Dify;
- Supabase migration;
- новый UI ради UI;
- глубокую перестройку всего workflow одним патчем.

## 9. Definition of Done к демонстрации

Демо готово, когда одновременно выполнено:

- топ-10 товаров отвечают по карточке, цене и фото;
- фото приходит один раз;
- price/media/card routes не вызывают LLM без необходимости;
- follow-up понимает текущий товар;
- trusted feedback проходит полный управляемый цикл;
- candidate не влияет на знания;
- smoke pack проходит не ниже 95%;
- нет открытых high runtime bugs по демонстрационным сценариям;
- 30-100 отзывов обработаны в трассируемые patterns;
- врачебно не подтвержденные claims явно отделены;
- два полных demo run проходят подряд;
- есть backup и проверенный rollback workflow.

## 10. Что нужно запросить у Виктора только при фактическом блокере

- точную Drive-папку с отзывами перед началом Testimonials MVP;
- выбор 10 демонстрационных товаров, если его нельзя надежно вывести из частоты запросов;
- подтверждение формулировки, если источники конфликтуют;
- доступ только если имеющийся реально перестал работать;
- решение по спорному бизнес-поведению, которое нельзя вывести из уже согласованных правил.

Не запрашивать повторно уже переданные доступы и не гонять пользователя проверять гипотезу, пока ее нельзя проверить самостоятельно.
