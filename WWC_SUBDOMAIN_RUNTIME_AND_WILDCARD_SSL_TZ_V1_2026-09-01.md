# WWC Subdomain Runtime и Wildcard SSL ТЗ V1

Дата: 2026-09-01
Статус: исполняемый срез по решению лида. Готовит платформу к массовому онбордингу личных поддоменных сайтов (цель — сотни партнёров) до прихода данных нового поддоменного сайта.
Основание: review лида от 2026-09-01 + собственные пробы AutoCoder (см. «Факты»).

## 0. Факты (проверено, не предполагается)

- Один nginx `server_name *.wwc.best`, один web-root, все поддомены отдают один dist. Отдельных копий нет.
- Данные партнёров зашиты в билд: `src/data/referrals.js`, `src/data/partner-pages.js`.
- `ReferralBootstrap.astro` импортирует весь реестр и встраивает его в HTML каждой страницы (`define:vars`). После API-резолва профиль склеивается с локальным: `local.name`, `local.photoUrl`, соцсети берутся только из локального профиля. Поправка лида подтверждена кодом.
- `deploy-with-backup.sh` всегда: полный `npm ci` → build → tar → `rsync --delete` в live root. Атомарного переключения нет (release-папка создаётся, но файлы копируются прямо в live).
- DNS: зона `wwc.best` — Spaceship (`launch1/launch2.spaceship.net`); зона `sysarch.pro` — Active.by (`ns1/ns2.activeby.net`). Это разные регистраторы.
- Пробы 2026-09-01: wildcard A-запись есть (`random.wwc.best` → `173.249.45.83`); TLS на случайном поддомене падает `SEC_E_WRONG_PRINCIPAL` — wildcard-сертификата ещё нет (multi-SAN); `sofiya.wwc.best` — 200; `media.sysarch.pro` — валидный HTTPS уже работает (HTTP 301 → HTTPS, cert verify ok).
- Spaceship имеет публичный API с управлением DNS-записями (docs.spaceship.dev; Terraform-провайдер `namecheap/spaceship` управляет `spaceship_dns_records`). Наличие API-ключа в аккаунте — проверить.

## 1. Ответ на вопрос лида: где тестить wildcard

Тестировать сразу на `wwc.best`, не на Active.by. Основания:

1. DNS-01 challenge для `*.wwc.best` в любом случае делается записью TXT в зоне `wwc.best` (Spaceship). Тест на `sysarch.pro` проверяет другую зону и другого регистратора и ничего не снижает для wwc.
2. `media.sysarch.pro` — одиночный хост, HTTPS у него уже работает; wildcard там не нужен.
3. Риск для прода около нуля: выпуск нового сертификата не трогает текущий; переключение nginx — отдельный контролируемый шаг.
4. Ручной выпуск для проверки занимает минуты и не требует API — автоматизация подключается вторым шагом.

## 2. Срез 1 — Wildcard SSL (первый, наименьший риск)

1. Выпустить wildcard `*.wwc.best` + SAN `wwc.best` отдельным cert-именем через DNS-01 (первый выпуск — вручную: TXT в зоне Spaceship).
2. Установить параллельно текущему SAN-серту; переключить nginx на wildcard; smoke: все 12 текущих хостов 200 + случайный поддомен с валидным TLS.
3. Автоматизировать renew через Spaceship API + certbot dns hook; `certbot renew --dry-run` обязан быть зелёным.
4. Обновить `03_Website/wwc-best/docs/PARTNER-SUBDOMAIN-ONBOARDING.md`: убрать шаг расширения SAN, зафиксировать «новый партнёр = данные, certbot не трогаем».

Приёмка: curl всех текущих поддоменов 200; random-поддомен валидный TLS; `renew --dry-run` 0.

Запреты: не переключать nginx до успешного выпуска и проверки; текущий SAN-серт не удалять до стабилизации; не менять n8n-маршруты и Telegram binding.

## 3. Срез 2 — Профиль API до полного публичного контракта (Core)

Расширить `GET /api/v1/public/ref/{code}` аддитивно до полного публичного контракта:

- `refCode`, `displayMode`, `enabled`, `profileVersion`;
- `consultant`: `displayName`, `photoUrl` (абсолютный URL media host), `shortBio`, `contactUrl`, `contactLabel`, `subdomain`, `tier`, `socials` (все, что сейчас только в локальном профиле);
- `theme`, `personalPageUrl`.

Источник: `Partners_Ref` (master, Google Sheet) → штатный structured sync → Core. В лист добавить недостающие поля (socials, theme, путь фото).

Приёмка: pytest на контракт + live-проверка GET для 2–3 реальных партнёров.

Запреты: не ломать текущую форму ответа (только аддитивные поля); сайт на переходный период остаётся совместимым.

## 4. Срез 3 — Bootstrap сайта на API-резолв

1. `ReferralBootstrap` v2: hostname → ref и весь профиль — из API; маппинг `samtsova → olga-samtsova` и подобные решается на Core по полю `subdomain`, не в сборке.
2. Из HTML убирается встроенный реестр. Локально остаётся только `organicProfile` (платформенные константы) и аварийный fallback без партнёрских персональных данных.
3. Переход по одному партнёру через существующий механизм `refApiCanaryRefs`.

Приёмка: Playwright smoke на 3 поддоменах — имя/фото/контакты приходят из API; при недоступном API — органический режим без ошибок в консоли.

Запреты: не публиковать партнёрские тексты в сборке; не убирать canary-флаги.

## 5. Срез 4 — partner-pages → runtime

Личная страница `/partner/`: статическая оболочка + контент из Core (эндпоинт профиля/страницы). После переноса всех карточек `partner-pages.js` удаляется из сборки.

Приёмка: `/partner/` у 2–3 партнёров полностью рендерится из API; текст сверен с master-листом.

## 6. Срез 5 — Медиа на media.sysarch.pro

Фото партнёров размещаются на `media.sysarch.pro` (хост уже HTTPS-валиден), путь по образцу `media/partners/...`; в dist не копируются. `photoUrl` в master-листе — абсолютные URL.

Приёмка: dist не содержит `/media/partners`; все фото открываются по HTTPS.

## 7. Срез 6 — Атомарный деплой

`deploy-with-backup.sh` v2: release-каталог → атомарное переключение symlink, хранить N последних релизов, мгновенный rollback, smoke после переключения.

Приёмка: тестовый деплой без 5xx в момент переключения; rollback проверен.

## 8. Порядок работ

1. Срез 1 (wildcard) — сразу, малый риск, независим от остального.
2. Срез 2 (Core-контракт) — параллельно, без deploy сайта.
3. Пилот нового партнёра end-to-end (данные даст владелец): строка в Sheet → sync → Core → сайт через runtime, без билда. Это и есть проверка целевой модели на живом случае.
4. Срезы 3–6 по мере готовности Core, каждый через canary.
