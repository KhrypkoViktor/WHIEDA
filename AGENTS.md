# WHIEDA: обязательный старт агента

Этот файл читается до анализа, правок, Git и deploy. Если факта нет в
канонических документах или живой системе, не придумывать его: сначала
проверить или задать владельцу один конкретный вопрос.

## Порядок чтения

1. Этот файл.
2. `WORK/README.md` и `WORK/PLATFORM_CURRENT_STATE.md` — что разрешено
   собирать в production и подтверждённое состояние живой системы.
3. `PROCESS/README.md` и `PROCESS/<актуальная задача>/STATE.md` — что уже
   сделано и что не принято.
4. Релевантный runbook в `backend/deploy/core/` перед работой с Core,
   Telegram или deploy.

`WORK` — утверждённые источники. `PROCESS` — черновики и отчёты, их нельзя
молча выдавать за production-правду.

## Среды и боты

| Среда | Бот | Профиль интерфейса | Назначение |
| --- | --- | --- | --- |
| Production | `@WHIEDA_Advisor_bot` (`whieda-advisor-bot`) | `minimal` | Только готовые партнёрские действия. |
| Staging | `@wwc_admin_staging_bot` (`wwc-cabinet-staging-bot`) | `full` | Доработка и проверка новых сценариев. |

Профиль задаётся только переменной окружения Core:
`PLATFORM_TELEGRAM_UI_PROFILE=minimal|full`.

Production `minimal` обязан показывать только `/cabinet`, `/invite`,
`/calculator`, `/support`; текстовая команда «сервисы» (тоннель к
администратору сервисов, заявки `#S-N`) разрешена владельцем 15.09.2026 —
администратор видит только «Клиент WWC · Заявка #S-N», без имени и ссылки.
Заявки живут в форум-группе (тема на заявку); группа регистрируется командой
`/forum` от владельца или администратора внутри группы, отдельно для каждого бота
(таблица `support_forums`, ключ — `binding_id`). В кабинете допустимы: личный сайт, копирование
реферальной ссылки, отправка приглашения, калькулятор и поддержка. Создание
сайта, продление, приём чека, списание бонусов и незавершённые действия не
показывать. Старая кнопка такого действия должна безопасно направлять к
ручному контакту, а не открывать частичный процесс.

Токены у ботов разные. База данных сейчас общая: staging годится для UI и
реальных проверок, но запрещены вымышленные люди, оплаты, начисления и
реферальные связи — они станут боевыми данными.

## Совместная работа агентов (владелец, 16.09.2026)

Одновременно работают три агента: **Core-агент** (бот WHIEDA: партнёрка,
подписки, оплаты, поддержка, советник, вход обновлений), **NSP-агент**
(tenant NSP), **Site-агент** (сайт wwc.best, заявки, данные партнёров). Один
репозиторий, одна общая база staging/prod. Чтобы не ломать друг друга:

1. **В `master` никто не пушит** до команды владельца. Каждый работает в
   своей ветке `<зона>/<тема>`: `core/…`, `nsp/…`, `site/…` — в своём
   git-worktree, не в чужом дереве и не в `D:\Projects\WHIEDA`.
2. **Слияние в `master` делает один агент** (сейчас — Core-агент) в конце,
   по команде владельца: `git rebase origin/master` → гейт зелёный → зона
   зелёная → `merge --ff-only`. Другие присылают: «ветка `nsp/…`, готово к
   слиянию, гейт зелёный».
3. **Зоны файлов** — `.github/zones.json`. Ветка меняет только файлы своей
   зоны и общие файлы (`settings.py`, `schema_requirements.py`,
   `postgres_testkit.py`, `conftest.py`, `release_core.ps1`, `zones.json`,
   `AGENTS.md`) — **только добавлением строк**, ничего не переименовывать и
   не удалять. Нужна правка в чужой зоне — одной строкой владельцу зоны, он
   делает сам в течение дня. Не «поправлю попутно».
4. **Проверка автоматическая**: `python .github/scripts/check_zone.py --base
   origin/master` перед тем, как объявить ветку готовой; GitHub Actions
   (`.github/workflows/gate.yml`) гоняет то же плюс фокус-тесты Core на
   каждом PR и каждой ветке. Красный чек — ветка не готова.
5. **Подпись**: в своём worktree `git config user.name "<Core|NSP|Site>-agent"`
   и `git config user.email "<имя>@whieda.local"`, чтобы в истории было
   видно, кто что сделал. Один общий `WHIEDA Codex` — больше нельзя.
6. **Никогда в git**: `__pycache__`, `*.pyc`, `.env`, `secrets/`,
   `node_modules/`. Перед коммитом `git status` — только свои файлы.
7. **Общая база**: миграции только `create … if not exists` /
   `add column if not exists`, применяются к общей базе один раз и
   записываются в `/opt/whieda-platform-core/migrations/APPLIED.log`; новые
   таблицы — в `schema_requirements.py` и `postgres_testkit.py`. Код,
   который читает колонку, не выкатывать раньше миграции.
8. **Релизы**: только из `master`, только Core-агент, только
   `release_core.ps1 -Target staging` → проверка владельца → `-Target core`
   тем же SHA. Перед релизом — сообщение в общий чат («релиз staging, 5 мин»).
9. **Документы**: свои — только в `PROCESS/<зона>-<тема>/STATE.md`; новых
   верхнеуровневых `.md` не заводить; `AGENTS.md` дополнять, не переписывать.

Что случилось 16.09 и чего это правило не допускает впредь: слияние 393
файлов в `master` без гейта задело чужие зоны (`routes.py`, `processor.py`,
`repository.py`), принесло `.pyc` и колонку, которой нет в базе — staging
падал на любом вопросе о товаре, пока владелец зоны не починил.

## Правило выпуска

1. Работать в отдельной feature-ветке. Не смешивать с чужими изменениями и не
   добавлять `__pycache__`, секреты или чужой незавершённый код.
2. Сделать целевые тесты и зафиксировать коммит.
3. Выпустить этот commit на staging только через
   `backend/deploy/core/release_core.ps1 -Target staging`.
4. Проверить конкретную новую функцию на staging. Для Telegram не проводить
   фальшивые финансовые тесты.
5. Выпустить **тот же SHA** на production через
   `release_core.ps1 -Target core`. Не выкатывать «текущий master» или другой
   произвольный commit вместо проверенного.
6. После deploy проверить `/health/ready`, ревизию, нужную Telegram-команду и
   обновить `PROCESS/<задача>/STATE.md`.

Изменение production-конфига, общей базы, nginx, DNS, webhooks и токенов —
отдельное рискованное действие. Нужны резервная копия, явная причина и
проверка после; не менять "заодно".

## Telegram

Перед изменением меню читать
`backend/deploy/core/TELEGRAM_COMMAND_MENU_RUNBOOK.md`.

Telegram хранит старую reply-клавиатуру на устройстве пользователя. После
перехода на компактное меню пользователь должен отправить `/start`; бот
уберёт старую клавиатуру и покажет кабинет. Не делать массовую рассылку для
этого без прямого решения владельца.

## Остановка

Остановиться и спросить владельца, если:

- задача требует реальной оплаты, начисления или смены владельца лида;
- staging-тесту нужны вымышленные данные в общей БД;
- неизвестно, какой commit или среда являются источником;
- изменение касается production и не прошло staging на том же commit.
